# Control Hub v2: 홈 화면, 장치 페이지, 오류 위치, 세션·사고 기록

작성 2026-11-15. 상태: 승인 대기. 앞 설계: `2026-11-14-control-hub-design.md` (tmux 리모컨 구조는 그대로 둔다).

## 1. 왜

control hub 는 **터미널 여러 개를 대신하는 bring-up·디버깅 컨트롤 타워**다. 로봇을 연결하고, 포트가 다 잡히는지 보고, 하나씩 켜고, 통신을 확인하고, 로그를 보고, 문제가 생기면 원인을 찾는다 (하민, 11/15).

"수집(팔+손+녹화)" 실행표는 가이드 순서를 옮긴 것일 뿐이고 나중에는 프로세스 하나가 된다. 그래서 화면의 중심을 **실행 순서에서 장치로** 옮긴다. hub 는 검증 후 녹화기와 합쳐지므로 장치 이름은 녹화기 스트림 이름에 맞춰 둔다.

현장에서 자주 나는 문제는 **LEAP 특정 모터가 안 잡히거나 도중에 끊기는 것**이다. 원하는 것은 "오류가 뜨면 어디서 떴는지 보이고, 그때 확인할 수 있는 것"이다. **모터를 계속 감시하는 것은 원하지 않는다**: 제어 주기에 영향을 주거나 꼬일 수 있는 복잡함보다 단순함이 낫다 (하민, 11/15).

지금 코드에서 알아 둘 것:

- LEAP 피드백은 16개를 한 번에 읽는다(sync read). SDK(dynamixel_sdk 4.0.3)는 응답 없는 첫 모터에서 멈추고, 예외 문구는 `feedback sync read failed for ID None` 이다 (`leap_v1.py:402`). 모터 번호가 없다.
- `leap_driver.read_feedback` 은 그 예외를 삼키고 `None` 을 돌려준다 (`leap_driver.py:30`). 로그에 안 남는다. 피드백은 기록 옵션(`--publish`, `--log-csv`, `--record-udp`)이 켜졌을 때만 읽는다 (`app.py:42`).
- 시작할 때 `connect()` 는 모터를 하나씩 확인하고, 빠진 것이 있으면 `Missing or unresponsive DYNAMIXEL IDs: [...]` 로 **번호를 찍고** 멈춘다. 끌 때 토크 OFF 가 안 된 모터도 `Torque-off was not acknowledged by motor IDs (...)` 로 번호가 찍힌다.
- `leap_check` 는 연결하며 16개를 하나씩 확인하고, 모터별 위치·온도·전압·하드웨어 오류를 출력한다 (`tools/check_hardware.py`). 이것이 "그때 확인하는" 도구다.

## 2. 목표, 하지 않는 것, 실패 조건

**목표**

- **홈 화면**: 장치 전체 상태, 도는 프로세스, 최근 문제를 한 화면에서 본다.
- **장치 페이지**: 로봇 PC·네트워크, 팔, LEAP, 글러브, 촉각, 손목 카메라, 외부 카메라. 장치마다 연결 정보, 관련 프로세스와 확인 도구, 마지막 확인 결과, 그 장치의 문제와 로그.
- **오른쪽 상태 패널**: 어느 화면에서든 ping 지연, 포트, 프로세스 요약, 문제 수.
- **오류 위치**: 로그에 오류가 뜨면 어느 장치(가능하면 몇 번 모터)인지 보여 주고, 그 자리에서 확인 도구로 간다.
- **세션 기록**: 한 번의 bring-up 동안 일어난 일(점검 변화, 프로세스 시작·종료, 로그 오류)을 시간순으로 파일에 남기고 다시 본다.
- **사고 폴더**: 오류가 뜰 때마다 그 오류를 기준으로 로그와 상태를 한 폴더에 모아 남긴다 (6.2).
- **장치 탐색 (대략)**: 지금 꽂힌 USB 장치와 시리얼 포트를 찾아 보여 준다 (5.5). 실물에 연결해 보며 다듬는다.

**하지 않는 것**

- 텔레옵 중 모터 상태를 계속 읽거나 보내는 것 (11/15 결정). 텔레옵 루프에 버스 읽기를 더하지 않는다.
- 장치를 잡은 프로그램이 hub 로 상태를 보내는 통로 (UDP 등). 녹화기와 합칠 때 다시 본다.
- hub 가 장치(시리얼, 카메라)를 직접 여는 것.
- 카메라 영상, 촉각 값 미리보기, rqt 띄우기. 영상은 녹화기 화면에서 본다 (11/15 결정). 카메라 장치 페이지는 정보(연결, USB 속도, 시리얼 번호, 관련 프로세스)만.
- **포트 자동 지정** (탐색한 포트를 명령에 자동으로 넣기). 추후 구현 (12장). 이번에는 찾아서 보여 주기만 한다.
- 녹화기와 지금 합치기.

**이렇게 되면 실패**

- hub 때문에 텔레옵·녹화기의 동작이나 주기가 달라진다.
- 오류가 로그에 떴는데 홈 화면에 안 보인다.
- 장치를 하나 추가하는 데 JS 를 고쳐야 한다 (YAML 로 되어야 한다).

## 3. 접근 방식

| | 방식 | 판단 |
|---|---|---|
| A | 장치를 잡은 프로그램이 상태를 계속 hub 로 보낸다 | 처음에 골랐으나 **뺐다** (11/15). LEAP 은 모터가 빠지면 읽기마다 수 ms~수십 ms 를 기다려 제어 루프를 늦출 수 있다 |
| **B** | **로그 분석 + 필요할 때 확인 도구** | **채택.** hub 혼자 한다. 텔레옵 코드는 오류를 로그에 남기는 한 줄 수준만 바꾼다 |
| C | 녹화기 `:8800` 실시간 값을 끌어온다 | 쓰지 않는다. 녹화기가 켜져야만 보이고 합칠 때 어차피 바뀐다 |

## 4. 화면

녹화기·지금 hub 와 같은 틀(왼쪽 메뉴, 흰 바탕, 색은 상태에만)에 3단 구성이다.

```text
┌────────────┬─────────────────────────────────────────────┬──────────────────────┐
│ Control Hub│ 홈                          세션 11/15 14:02 ▸│ 상태                 │
│ ■ 홈       │ ┌ 로봇 PC ─┐┌ 팔 ──────┐┌ LEAP ────┐┌ 글러브 ┐ │ ● 로봇 ping   0.4ms  │
│   장치     │ │● 0.4ms   ││● 준비됨  ││✕ 오류    ││● 켜짐  │ │ ● ssh / 컨테이너     │
│    로봇 PC │ │ssh·zenoh ││          ││ID 7 응답X││        │ │ ● zenoh :7447        │
│    팔      │ └──────────┘└──────────┘└──────────┘└────────┘ │ ● Manus 동글         │
│    LEAP    │ ┌ 촉각 ────┐┌ 손목캠 ──┐┌ 외부캠 ──┐           │ ✕ LEAP ttyUSB0       │
│    글러브  │ │● ttyACM0 ││● USB3    ││○ 없음    │           │   latency 1 ✓        │
│    촉각    │ └──────────┘└──────────┘└──────────┘           │ ● Paxini ttyACM0     │
│    손목캠  │ 프로세스  ● manus  ● zenohd  ● arm  ✕ leap_manus │ ● 손목캠 USB3        │
│    외부캠  │ 최근 문제                                      │ ○ 외부캠             │
│   실행표   │ 14:31:07 LEAP  모터 응답 없음: 7  [leap_check ▸]│ ───────────          │
│   로그     │ 14:30:52 팔    BULK_READ_FAIL ×3 (무시)        │ 프로세스 4/5         │
│   전체     │ 14:28:10 손목캠 USB 다시 잡힘                   │ 문제 2 ▸             │
└────────────┴─────────────────────────────────────────────┴──────────────────────┘
```

- **홈**: 장치 칸(상태 색 + 핵심 한 줄: 마지막 오류나 연결 정보), 프로세스 한 줄, 최근 문제(최신순). 칸을 누르면 장치 페이지, 문제 줄을 누르면 그 로그 위치로 간다. 문제 줄에 그 장치의 확인 도구 버튼이 붙는다.
- **장치 페이지** 공통 틀:
  1. 연결: 경로, by-id, USB 시리얼 번호, USB 속도, 권한, latency timer, ping 지연 (hub 가 장치를 열지 않고 본 것)
  2. 관련 프로세스(켜기·끄기, 상세는 기존 프로세스 화면)와 확인 도구 버튼
  3. **마지막 확인 결과**: 그 장치 확인 도구의 마지막 실행 시각, 종료 코드, 출력. LEAP 은 아래 모터 표로 보인다
  4. 이 장치의 문제와 사건 (세션 기록에서 이 장치 것만)
- **LEAP 모터 표**: 16칸 (ID, 관절 이름). 두 곳에서 채운다.
  - 로그 오류에 모터 번호가 있으면 그 칸을 빨갛게 ("14:31 응답 없음").
  - `leap_check` 를 돌리면 그 출력으로 칸마다 응답 여부, 위치, 온도, 전압, 하드웨어 오류를 채운다 (확인 시각 표시).
  - 텔레옵이 LEAP 포트를 잡고 있으면 `leap_check` 는 못 돈다 (기존 `conflicts`). 버튼을 누르면 "먼저 leap_manus 를 끈다"가 나온다. 끄는 확인 항목(손에 물체 없음)은 그대로다.
- **오른쪽 상태 패널**: 지금 왼쪽 아래 "사슬"을 옮기고 넓힌 것. 점검 결과, 장치 요약, 프로세스 수, 문제 수. 모든 페이지에서 보이고, 좁은 화면(1100px 미만)에서는 위쪽 띠로 접는다.
- **실행표**: 지금의 "실행" 페이지 그대로. 메뉴에서 홈 아래로 내린다.
- **로그**: 세션 목록 → 사건 시간표(장치·수준 필터) → 사건을 누르면 그 프로세스 로그의 해당 줄로 간다.
- **전체**: 지금 그대로.
- **연결** 페이지와 `chains` 는 홈·장치 페이지가 대신하므로 지운다.

## 5. 장치 정의와 오류 위치

### 5.1 `devices:` (hub.yaml 새 구역)

```yaml
devices:
  leap:
    title: LEAP Hand
    kind: leap                 # 화면 상세 틀: leap 만 특별(모터 표). 나머지는 generic
    recorder_stream: hand      # 녹화기 스트림 이름 (합칠 때 연결점)
    checks: [leap_port]        # 연결 정보에 쓰는 점검
    processes: [leap_manus, leap_leader]
    tools: [leap_check, leap_zero]   # 확인 도구. 첫 번째가 문제 줄의 버튼
    events:                    # 로그 줄 -> 장치 사건. 이름 붙은 그룹이 값이 된다
      - {match: "Missing or unresponsive DYNAMIXEL IDs: \\[?(?P<motors>[\\d, ]+)", level: bad, text: "모터 응답 없음: {motors}"}
      - {match: "Torque-off was not acknowledged by motor IDs \\(?(?P<motors>[\\d, ]+)", level: bad, text: "토크 OFF 미확인: {motors}. 5V 차단"}
      - {match: "Feedback unavailable for DYNAMIXEL ID (?P<motors>\\d+)", level: bad, text: "모터 {motors} 피드백 없음"}
      - {match: "\\[leap\\] feedback read failed", level: warn, text: "LEAP 읽기 실패 (모터 번호 모름). leap_check 로 확인"}
```

- 장치 7개: `robot`, `arm`, `leap`, `glove`, `tactile`, `cam_wrist`, `cam_ext`. `recorder_stream` 은 리스트도 된다 (`arm: [arm_state, arm_action]`).
- `events` 는 그 장치의 `processes` 와 `tools` 로그에 적용한다. 기존 `hints`(조치 문구)와는 따로다. 같은 줄에 둘 다 맞으면 사건으로 남기고 힌트도 붙인다. 같은 사건은 1초에 한 번만 센다 (그 이상은 횟수만 올린다).
- `motors` 그룹이 있으면 숫자를 모두 뽑아 LEAP 모터 표의 해당 칸에 표시한다.
- 장치에 걸리지 않은 프로세스의 오류(지금의 일반 오류 탐지)는 "기타"로 홈에 보인다. 오류가 안 보이는 일이 없게.
- **장치 상태 색** = 연결 점검, 관련 프로세스 상태, 최근 60초의 bad 사건 중 가장 나쁜 것. 계산은 서버 한 곳(`devices.py`)에서.
- `chains` 가 설정에 남아 있으면 검증 오류("v2 에서 없어짐, devices 로 옮긴다")를 낸다.

### 5.2 `leap_check` 출력 읽기

- `leap_check` 의 출력 줄(`Motor IDs/model numbers`, `Positions`, `Temperatures`, `Input voltages`, `Hardware errors`, `Missing or unresponsive ...`)을 hub 가 읽어 모터 표를 채운다. 파서는 `kind: leap` 전용 한 함수다.
- `leap_check` 코드는 바꾸지 않는다. 출력 형식이 바뀌면 표가 비고 원래 출력이 그대로 보인다.

### 5.3 텔레옵 코드 변경 (최소)

`leap_driver.read_feedback` 이 읽기 실패를 삼킬 때 **로그에 한 줄** `[leap] feedback read failed: <원래 메시지>` 를 찍는다. 같은 줄은 1초에 한 번까지만 찍는다.

- 버스 읽기를 더하지 않고, 재시도 횟수나 루프는 바꾸지 않는다. 기록 옵션이 꺼져 있으면 지금처럼 아무것도 읽지 않으므로 이 줄도 안 찍힌다.
- 이 변경은 따로 커밋한다.

### 5.4 점검 늘리기 (장치를 열지 않는 것만)

`serial` 점검의 대상은 지금처럼 경로(`/dev/ttyUSB0`)로 적는다. by-id 로 적는 것은 포트 자동 지정 때 한다.

- `ping`: 지연 ms 를 결과에 넣는다.
- `serial` (새 종류): `/dev/serial/by-id/` 패턴으로 찾는다. 결과: 실제 경로(`ttyUSB0`), USB 시리얼 번호, 읽기·쓰기 권한, FTDI latency timer (`/sys/bus/usb-serial/devices/<tty>/latency_timer`, 1 이 아니면 경고: USB 를 다시 꽂으면 16 으로 돌아간다). LEAP 이 `ttyUSB1` 로 바뀌는 문제도 잡는다.
- `usb` (지금 있는 종류를 넓힌다. 지금은 `lsusb -d`): sysfs 에서 vendor:product (선택: 시리얼 번호)로 찾는다. 결과: 있음, USB 속도(480/5000 Mbps). 손목캠이 USB2 로 잡히면 경고. 지금 `command: lsusb | grep` 으로 쓰는 Manus 동글, RealSense 점검을 이것으로 바꾼다.
- 점검 결과가 바뀔 때마다 세션 기록에 사건으로 남긴다 ("LEAP USB 사라짐 14:28:03", "다시 잡힘 14:28:10").

### 5.5 장치 탐색 (대략, 보여 주기만)

- "장치 탐색" 화면(또는 로봇 PC·네트워크 아래 칸): sysfs 와 `/dev/serial/by-id/` 를 읽어 지금 꽂힌 것을 표로 보여 준다. 열: 경로(`ttyUSB0`, `ttyACM1`, `video*`), by-id 이름, vendor:product, 제조사·제품 이름, USB 시리얼 번호, USB 속도, 버스 위치.
- 알려진 vendor:product 에 이름표를 붙인다 (설정 `known_usb`: FTDI → "LEAP?(FTDI)", Intel 8086:0b5b → "D405", 8086:0b3a → "D435i", Manus 동글 등). 확실하지 않으면 물음표.
- 설정의 점검(`leap_port: /dev/ttyUSB0` 등)과 다르게 꽂혀 있으면 표시한다 ("LEAP 이 ttyUSB1 에 있는 것 같다"). 고쳐 주지는 않는다.
- 꽂고 빼면 다음 점검 주기에 표가 바뀌고 세션 기록에 사건으로 남는다.
- 장치를 열지 않는다. 실물에 연결해 보면서 이름표와 열을 정리한다.

## 6. 세션 기록

### 6.1 세션

- **세션** = hub 를 켠 때부터. 화면의 "새 세션" 버튼으로 끊는다. 폴더: `~/.local/state/control_hub/sessions/<YYYY-MM-DD_HHMMSS>/`
  - `events.jsonl`: 사건 한 줄씩 `{t, dev, source: check|process|log, level: info|warn|bad, text, data, run, line}`. 점검 변화, 프로세스 시작·준비·종료(종료 코드), 로그 사건, 확인 도구 결과 요약. `run`, `line` 은 로그 위치다.
  - `runs.json`: 이 세션에서 돈 프로세스 실행과 로그 파일 경로 (로그 파일은 지금 위치 그대로, 복사하지 않는다).
- 로그 사건은 hub 가 로그를 읽을 때 생기므로 `line`(로그 파일 안의 줄 번호)을 바로 알 수 있다. 사건을 누르면 그 줄로 간다.
- **내보내기**: 세션 폴더 + 관련 로그를 zip 하나로 받는 버튼.
- 보관: 세션 30개를 넘으면 오래된 것부터 지운다 (설정 `keep_sessions`).

### 6.2 사고 폴더 (오류 기준 기록)

bad 사건이 생길 때마다 세션 안에 폴더 하나를 만든다.

```text
sessions/2026-11-15_140210/incidents/
  143107_leap_모터응답없음/
    summary.md        # 언제, 어느 장치, 무슨 오류(원래 줄), 힌트, 그때 켜져 있던 프로세스와 상태
    leap_manus.log    # 오류 직전 200줄 + 직후 30초
    others/           # 같은 시간대(직전 60초 ~ 직후 30초) 다른 실행 중 프로세스 로그
    checks.json       # 그 순간 점검 결과와 장치 탐색 표
    leap_check.txt    # 그 뒤 5분 안에 그 장치의 확인 도구를 돌렸으면 결과
```

- 같은 장치에서 30초 안에 같은 사건이 반복되면 새 폴더를 만들지 않고 `summary.md` 의 횟수와 마지막 시각만 올린다.
- "직후 30초"는 30초 뒤에 채워 넣는다. 그 전에 hub 가 꺼지면 있는 데까지만 남는다.
- 화면: 홈의 "최근 문제" 줄과 로그 페이지에서 사고를 누르면 폴더 내용이 보이고 zip 으로 받는다.
- 폴더 이름의 설명은 사건 문구를 줄여 쓴다 (파일 이름에 못 쓰는 글자는 뺀다).

## 7. 녹화기와 합칠 때 (대략)

- 장치 id ↔ 녹화기 스트림 이름은 `recorder_stream` 이 잇는다. 합치면 녹화기 스트림의 Hz, 영상, 촉각 그림이 장치 페이지의 "마지막 확인 결과" 자리 옆에 들어온다.
- 화면 틀이 같으므로 장치 페이지 틀을 그대로 쓴다.
- 지금은 서로 import 하지 않는다.

## 8. 구현 범위와 순서 (제안)

1. 설정: `devices` 읽기·검증, `chains` 제거, `serial` 점검과 `usb`·`ping` 확장.
2. 서버: 장치 상태 계산(`devices.py`), 로그 사건 추출(`logscan.py` 확장), 세션 기록, `leap_check` 출력 파서, API.
3. 화면: 홈, 장치 페이지(공통 틀 + LEAP 모터 표), 오른쪽 상태 패널, 로그 페이지, 메뉴 정리.
4. `hub.example.yaml`, `hub.fake.yaml`: 장치 7개, 가짜 LEAP 오류를 내는 가짜 프로세스와 가짜 `leap_check`.
5. 장치 탐색 화면 (5.5), 사고 폴더 (6.2).
6. `leap_teleop`: 5.3 의 로그 한 줄 (따로 커밋).
7. `control_hub_usage.md` 갱신, 현장 확인 항목 추가.

## 9. 테스트

- 설정: `devices` 검증 오류 (없는 check/process/tool id, 잘못된 정규식, 남은 `chains`).
- 로그 사건: 실제 LEAP 문구 샘플(`Missing or unresponsive DYNAMIXEL IDs: [3, 7]`, 토크 OFF 미확인, `[leap] feedback read failed`)로 모터 번호 추출, 1초 제한, 힌트와 동시 적용, 장치 없는 프로세스 오류가 "기타"로 남는지.
- `leap_check` 파서: 정상 출력, 빠진 모터 출력, 형식이 다른 출력.
- 장치 상태 계산: 점검·프로세스·사건 조합 표.
- 점검: 가짜 sysfs 디렉터리로 `serial`, `usb` (속도, latency timer).
- 세션 기록: 사건 순서, 새 세션 끊기, 보관 개수, 사건 → 로그 줄.
- 사고 폴더: 폴더 내용, 30초 반복 묶기, 직후 30초 채우기, 확인 도구 결과 붙이기.
- 장치 탐색: 가짜 sysfs·by-id 디렉터리로 표, 이름표, "설정과 다른 위치" 표시.
- `leap_driver`: 실패 시 줄이 찍히고 1초 제한, 반환값은 지금과 같은 `None`.

**현장 확인 항목**: LEAP 모터가 빠졌을 때 실제로 어떤 줄이 찍히는지 보고 `events` 정규식을 맞춘다. 장치 탐색 표에 LEAP, Paxini 보드 두 개, 카메라, Manus 동글이 각각 구분되어 보이는지 (특히 Paxini 보드의 USB 시리얼 번호가 서로 다른지), USB 속도, latency timer 표시가 맞는지.

## 10. 내가 정한 것 (바꿀 수 있다)

- 장치 7개와 id. LEAP 만 전용 상세(모터 표), 나머지는 공통 틀.
- 텔레옵 변경은 로그 한 줄뿐, 따로 커밋.
- `chains` 와 "연결" 페이지 제거.
- 같은 사건 1초 제한, 장치 상태는 최근 60초 사건 기준.
- 세션 30개 보관, hub 를 켤 때 새 세션.
- 사고 폴더: 직전 200줄 + 직후 30초, 같은 사건 30초 묶기.

## 11. 만드는 사람에게 남기는 것

- 장치 칸·모터 표의 세부 배치, 문구, 색 경계.
- `events` 정규식은 실제 로그를 보고 맞춘다. 위 예시는 지금 코드의 문구에서 뽑았다.
- 장치별 `checks`/`processes`/`tools` 배정은 지금 `hub.example.yaml` 의 항목을 나눠 담는다.
