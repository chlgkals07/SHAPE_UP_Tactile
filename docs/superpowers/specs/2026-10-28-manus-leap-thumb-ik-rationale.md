# 설계 근거: 손가락 affine + 엄지 IK

- 작성일: 2026-10-28
- 관련: [spec](2026-10-27-manus-leap-retargeting-design.md), [plan](../plans/2026-10-28-manus-leap-retargeting.md)
- 결정: 검지·중지·약지는 관절별 affine, 엄지는 affine과 IK를 둘 다 구현하고 `--thumb`로 고른다 (기본 IK). 굽힘–측면 결합 제한은 넣고, pinch snap·dex-retargeting은 미룬다.
- **개정 (2026-10-29)**: 엄지 IK의 자세 선택을 지문 면 항에서 **BiDex 방식(엄지 끝 + IP 관절 두 점)**으로 바꿨다. 엄지 affine 대응도 BiDex 직접 매핑 예제를 따랐다. 7절.

## 1. 예전 방식 (shinjju1209/leap-hand@ddfabaa) = affine

`hand_angles.py` + `neutral_calibration.py`:
1. 웹캠 MediaPipe 21점 → 사람 관절각 16개
2. 편 손(neutral)과 주먹(closed)을 1.5 s씩 기록, 중앙값
3. 굽힘: `q = clip((h − h_open) / (h_closed − h_open), 0, 1) × q_fist` (q_fist = 90/100/80°, 엄지 0/60/75/70°)
4. 측면: `q = h − h_open`

이 식은 `q = g·h + b` 꼴(관절마다 직선 하나)이라 affine이다. `g = q_fist / (h_closed − h_open)`, `b = −g·h_open`.

## 2. LEAP 엄지 구조 (URDF FK로 직접 계산)

`dex-urdf` `leap_hand_right.urdf`, 모든 관절 0에서 손바닥 좌표계 기준:

| 관절 (우리 이름) | 축 | 하는 일 | 범위 |
|---|---|---|---|
| 12 `thumb_cmc_side` | 손가락과 평행 | 엄지 전체를 손바닥 앞으로 돌림 | −20° ~ 120° |
| 13 `thumb_cmc_flex` | 엄지 길이 방향에 가까움 | 사실상 비틀기(roll) | −27° ~ 140° |
| 14 `thumb_mcp_flex` | 손바닥 법선 | 굽힘, 13번에 따라 굽는 평면이 바뀜 | −69° ~ 109° |
| 15 `thumb_ip_flex` | 14번과 평행 | 굽힘 | −77° ~ 108° |

- 0 자세에서 엄지는 손바닥 평면 안에서 옆으로 뻗은 L자다.
- 사람 엄지의 opposition은 CMC 안장관절 하나에서 벌림·굽힘·안쪽 회전이 함께 일어난다. LEAP는 이를 12번(돌리기) + 13번(비틀기)으로 나눴다. 이름은 같아도 1:1 대응이 아니다.
- 예전 코드는 "손바닥 평면 안 벌림 → 12번", "손바닥 밖으로 나온 각 → 13번(비틀기)"로 연결했다. 움직임이 엇갈려 대응된 것으로 보인다.
- 손가락은 다르다. MCP 굽힘(1번) 위에 측면(0번)이 얹힌 universal 구조이고, LEAP 논문도 손가락은 관절각을 그대로 매핑할 수 있다고 한다.
- 우리 `ANGLE_NAMES` 인덱스 = 모터 ID = URDF 관절 이름 `"0"`~`"15"`이고, `SIM_MIN/MAX_RADIANS`는 URDF limit과 같다. 따라서 우리 각도를 라디안으로 바꾼 값이 URDF q다. 영점은 실측 open이므로 offset knob을 둔다.

## 3. URDF 수치 검증

엄지 4관절 + 검지 3굽힘에 대해, 엄지 끝–검지 끝 거리를 LM으로 최소화했다 (무작위 시작점 30개):

| 조건 | 최소 거리 | 엄지 q (°) |
|---|---|---|
| 12번을 0°로 고정 | 0.0 mm | [0, 67, 96, 11] |
| 전부 자유 | 0.0 mm | [58, 28, 0, 108] |

- 12번이 0°여도 13·14번 조합으로 pinch에 도달한다. 대화 중 "12번이 0이면 엄지가 못 나온다"고 한 것은 틀렸다.
- **문제는 도달 가능성이 아니라 해 선택이다.** 같은 손끝 위치를 만드는 엄지 자세가 여럿이다(관절 4개 vs 위치 3차원). 그래서 IK에는 위치 외에 자세를 고르는 항이 필요하다.
- 가정: 우리 0 = URDF 0, 부호 같음. 실물에서 확인한다.

## 4. 문헌 근거

| 근거 | 내용 |
|---|---|
| [2609.06009](https://arxiv.org/html/2609.06009) | Manus → LEAP. 손가락은 관절별 affine(편 손·반쯤·주먹 3점 최소제곱), 엄지는 손끝 IK + opposition 항. `min ‖r_x‖² + λo‖r_o‖² + λs‖q − q_prev‖²`, λo = 0.2, λs = 0.05, LM, warm start, 보통 10회 미만 수렴. 직접 매핑은 "지연이 없지만 엄지–검지 opposition을 잃는다"고 서술 |
| [LEAP Hand](https://arxiv.org/html/2309.06440) | 손가락 관절이 사람과 비슷해 관절각을 직접 매핑 |
| [RAPID Hand](https://arxiv.org/pdf/2510.16931) | 직접 매핑은 주먹 때 손가락 충돌, 부자연스러운 자세 |
| [dex-retargeting](https://github.com/dexsuite/dex-retargeting) | LEAP 설정은 DexPilot, `scaling_factor: 1.6` |
| [Feel Robot Feels](https://arxiv.org/pdf/2603.28542) | 엄지–손가락 opposition 유지가 조작 성공에 중요해 제약으로 넣음 |

**한계**: 엄지 affine과 IK를 같은 손·글러브에서 직접 비교한 실험(ablation)은 찾지 못했다. 2609.06009도 정성적 이유만 든다.

**반대 사례**: [quest3-dexterous-teleop](https://github.com/ismael-esp/quest3-dexterous-teleop) (Quest 3 → Allegro)는 손끝만 맞추는 DexPilot에서 뿌리 쪽 관절이 떠서 주먹이 10~50%만 닫혔고, 엄지 MCP가 늘 반쯤 굽어 있었다. 그래서 엄지를 각도 매핑으로 되돌리고 5.5 cm 안에서만 IK로 붙였다.

## 5. 결정

### (개정 전) 엄지 IK: 위치 + 지문 면 방향 + affine prior + smoothing
> 2026-10-29에 7절의 BiDex 방식(끝 + IP 두 점)으로 바뀌었다. 아래는 기록으로 남긴다.

    min ‖f(q) − p*‖² + λo‖pad(q) − dir(q)‖² + λp‖q − q_aff‖² + λs‖q − q_prev‖²

- `p*`: 사람 엄지 끝을 LEAP 손바닥 좌표계로 옮긴 목표 (회전 R, 스케일 s ≈ 1.6, 엄지 뿌리 기준). 위치 잔차는 cm 단위
- `pad(q)`: 엄지 지문 면 법선 = IP 관절을 조금 더 굽힐 때 손끝이 움직이는 방향 (URDF에서 수치로 계산)
- `dir(q)`: 엄지 끝 → LEAP 검지 끝마디 중앙 방향. 둘을 맞추면 지문 면이 손가락을 향한다
- `q_aff`: 엄지 affine 결과. 위치만 맞추는 IK가 관절을 띄우는 문제(반대 사례)를 막는다
- `q_prev`: 이전 해. 해가 프레임마다 다른 쪽으로 튀는 것을 막는다

### 엄지 affine도 남긴다
- 키포인트가 없을 때의 fallback, IK의 prior, 그리고 **pinch 시험에서 IK와 비교할 기준**(문헌에 ablation이 없으므로 우리가 직접 한다).

### 장단점

| | affine (손가락) | IK (엄지) |
|---|---|---|
| 맞추는 것 | 관절 각도 | 손끝 위치와 엄지가 마주 보는 방향 |
| 장점 | 단순, 결과가 늘 같음, 지연 없음, 관절 하나만 보면 디버깅 가능, 글러브 좌표계 오차에 둔감 | 축이 다른 엄지 처리, pinch 접촉, 손 크기 차이를 스케일 하나로 흡수, URDF만 바꾸면 다른 손에 적용 |
| 단점 | 관절 1:1 대응이 전제, 접촉 보장 없음 | 손바닥 정렬·스케일 오차가 손끝 오차로 커짐, 키포인트 품질 의존, λ 튜닝, 원인 찾기 어려움 |

### 구현 중 수정: 2609.06009의 opposition 항은 지문 면을 돌리지 못한다
- 논문의 항 `n̂(q) = unit(index_tip − thumb_tip(q))`는 q에 **엄지 끝 위치를 통해서만** 의존한다 (논문도 그렇게 적었다). 손끝 위치가 같으면 값이 같으므로, 같은 위치를 만드는 여러 자세 중 하나를 고르지 못한다. 실제로는 위치 목표를 조금 옮기는 효과뿐이다.
- URDF로 확인: 검지 pinch 자세 하나에 대해 엄지 끝이 2 mm 안에 닿는 IK 해 34개를 찾았고, 지문 면이 검지 쪽을 향하는 정도(cos)가 −0.1 ~ 0.26 이상으로 제각각이었다.
- 그래서 엄지 **끝마디의 방향**(지문 면 법선)을 쓰는 항으로 바꿨다. 이 항은 13번(비틀기)처럼 위치를 바꾸지 않는 움직임에 반응한다. 테스트(`test_pad_term_turns_the_pad_toward_the_index_finger`)가 항을 켜면 지문 면이 검지 쪽으로 더 향하는 것을 확인한다.
- 목표 방향은 검지 **끝**이 아니라 **끝마디 중앙**이다. pinch에서 두 손끝이 닿으면 끝–끝 방향이 정의되지 않기 때문이다.

### 실시간성 (맥에서 측정, 50 Hz 틱 = 20 ms)
- 도달 가능한 목표: 틱당 중앙값 약 1.6 ms, 손끝 오차 중앙값 0.1 mm (p95 0.5 mm).
- 도달 불가능한 목표(사람 엄지가 LEAP 작업공간 밖): 반복 40회를 매번 다 써서 최대 약 11 ms → **틱당 10회로 제한**(최대 약 3 ms), 남은 수렴은 다음 틱의 warm start가 잇는다.

가장 큰 위험은 IK 계산이 아니라 **손바닥 정렬 캘리브레이션**이다. 사람 손바닥 좌표계는 매 샘플 키포인트(wrist, index/middle/pinky MCP)로 다시 만들므로 손목 회전과 글러브 좌표 단위에는 영향받지 않는다. 남는 위험은 좌표계 손잡이(handedness)가 반대인 경우(거울상)다. 편 손에서는 엄지가 손바닥 평면 안에 있어 거울상이 드러나지 않으므로, 캘리브레이션 도구는 **주먹**에서 엄지가 손바닥 앞/뒤 어느 쪽인지를 LEAP 주먹 자세와 비교해 경고한다(`thumb_ik.flip_normal`).

## 6. 함께 검토한 항목

| 항목 | 결정 | 이유 |
|---|---|---|
| 굽힘–측면 결합 제한 | **포함** | `|side| ≤ side_max × (1 − flex/flex_max) + side_floor`. 3~5줄. LEAP 측면 범위가 ±60°라 주먹 때 글러브 측면 노이즈로 이웃 손가락과 충돌할 수 있다(RAPID Hand 보고). 손가락을 굽힌 채 벌리는 동작은 거의 없다 |
| pinch snap | 보류 | 사람 손끝이 가까우면 IK 목표를 LEAP 손끝으로 강제. 주먹·원통 잡기에서 오작동 위험, 임계값 튜닝 필요. IK 단독 pinch 시험에서 틈이 남을 때 추가 (10줄 내외) |
| dex-retargeting | 보류 | 의존성(pinocchio, nlopt)과 ROS 시스템 numpy 충돌 위험, 손가락까지 최적화로 바뀌면 affine의 예측 가능성 상실(반대 사례가 이 방식). ROBOTIS 손 단계에서 재검토 |
| 혼합 행렬 `q = W·h + b` | 제외 | 엄지 문제는 기구학 차이라 선형으로 풀리지 않고, 캘리브레이션 자세 수 대비 파라미터가 많다. LEAP 텔레옵 관행에도 없다 |

## 7. BiDex 공식 코드 반영 (2026-10-29)

출처: [leap-hand/Bidex_Manus_Teleop](https://github.com/leap-hand/Bidex_Manus_Teleop) (MIT), [BiDex 논문](https://arxiv.org/html/2411.13677v1).

### 코드가 하는 일
- **리타게팅** (`ros2/telekinesis/telekinesis/leap_ik.py`): 손가락 4개 모두 IK. 손가락마다 목표가 **두 점**(끝 바로 전 관절 + 손끝, DexCap 방식). pybullet `calculateInverseKinematics2`, `IK_DLS`, 50회. 스케일 1.6 (x만 추가 1.15배), 2 mm offset 등 수동 보정. prior·smoothing·방향 항 없음.
- **직접 매핑 예제** (`python/MANUS_LEAP_example.py`): 관절별 affine을 손으로 맞춘 배율(1.5, 3, −2.5)과 offset으로. LEAP 12번 ← `ThumbMCPStretch`, 13번 ← `ThumbMCPSpread`. README: "이 모드에서는 엄지가 좋을 수 없다".
- **데이터 경로**: Manus SDK 2.4 C++ 클라이언트 → ZMQ → ROS 2. 코드 주석: Linux Integrated 모드에서 스켈레톤 노드 **순서가 뒤섞임**. README: Manus가 공식 ROS 2 패키지를 냈다.

### 반영한 것
| 항목 | 이전 | 이후 | 이유 |
|---|---|---|---|
| 엄지 IK 자세 선택 | 지문 면 법선이 검지 끝마디를 향하게 (자체 휴리스틱) | **엄지 IP 관절 위치도 목표** (`ip_weight` 0.3, 끝보다 약하게) | 사람 엄지가 실제로 향하는 방향을 따른다(항상 검지를 향하지 않음). 논문 근거("정확한 pinch와 엄지 위치"). 아래 수치 |
| 엄지 affine 대응 | 12 ← Spread(배율 매핑), 13 ← Stretch | **12 ← ThumbMCPStretch, 13 ← ThumbMCPSpread**, 12도 편 손~주먹 비율 매핑 + `fist_override_deg` | BiDex 예제와 같은 대응. 손으로 맞춘 큰 배율 대신 캘리브레이션 두 점이 배율을 정한다 |

| ergonomics 이름 | 하나 | SDK 3.1.1 이름 변경 별칭 (`ThumbMCPSpread` → `ThumbSpread`) | Manus 문서 |

### 반영하지 않은 것
- pybullet: numpy LM으로 같은 역할 (의존성 추가 없음).
- 손가락 IK: affine 유지 (LEAP 논문 근거). 부족하면 BiDex처럼 DIP + 손끝 두 점 IK로, 같은 LM 코드 재사용.
- x축 1.15배, 2 mm offset 같은 수동 보정: 필요해지면 실물에서.

### 수치 검증 (URDF, 사람 손 = LEAP 크기의 합성 데이터)
엄지가 편 상태에서 목표 자세까지 0.8 s(50 Hz) 동안 부드럽게 움직이고, IK는 매 틱 이전 해에서 시작:

| 목표 엄지 (°) | 끝만 (`ip_weight` 0): 자세 오차 최대 | 끝 + IP (0.3): 자세 오차 최대 |
|---|---|---|
| [8, 21, 64, 47] | 12.7° | 0.9° |
| [8, 39, 38, 13] | 28.1° | 2.7° |
| [66, 10, 31, 41] | 9.1° | 0.8° |
| [39, 53, 59, 77] | 16.3° | 1.9° |
| [26, 58, 56, 23] | 44.1° | 2.8° |

두 경우 모두 엄지 끝 오차는 0.0 mm다. **끝만 맞추면 위치는 맞아도 자세가 9~44° 어긋나고, IP를 더하면 3° 이내로 따라간다.** 틱당 계산 중앙값 0.9 ms, 최대 4.5 ms.

### 알려진 한계
- **차가운 시작(cold start)의 local minimum**: 이전 해 없이, 실제 자세와 멀리 떨어진 affine 엄지에서 시작하면 관절 한계에 걸린 해로 수렴할 수 있다 (편 손 0°에서 [20, 65, 55, 50]°로 바로 풀었을 때 13·15번이 한계에 붙음). 연속으로 따라가면 생기지 않았다. 시작·재시작(입력 0.5 s 끊김, 키포인트 손실 후)은 affine 엄지에서 하므로 **affine 대응이 대략 맞아야** 한다. 실물에서 문제가 되면 재시작 때 여러 시작점을 시도한다.
- 사람과 LEAP 엄지 마디 비율이 달라 두 점을 동시에 정확히 맞출 수 없다. `ip_weight`를 끝보다 작게 둔 이유이고, 실물에서 조정한다.
