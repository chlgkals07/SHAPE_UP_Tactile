## 2. 새 LEAP 손 bring-up

순서: `leap_check` → 편 손에서 5V 껐다 켜기 → `calibrate_motors --force` → `leap_check --torque-test` → `joint_test` 16관절.
이전 손의 영점은 `user_pc/config/hardware_motors.old_hand_20261112.yaml`(gitignore)에 남겼다.

**ID 11(약지 끝 마디) 혼이 180° 돌아가 조립됐었다.**
- 1차 기록 4.52 rad, 2차 6.286 rad(= 360°, 0~2π 밖). 5V를 껐다 켜고 `leap_check`를 하니 ID 11만 −179.8°였다.
- 편 자세가 모터 0°/360° 경계에 걸리면, 켤 때마다 0° 또는 359°로 읽혀 영점 대비 한 바퀴 차이가 난다. 코드는 이 경계를 처리하지 않는다.
- 손끝 마디를 빼고 혼을 180° 돌려 다시 끼웠다 → 3.128 rad (이전 손과 0.1° 차이).
- **확인법**: 영점 기록 전 `leap_check`의 `Positions`가 1·5·9번(약 −85°)을 빼고 모두 0 근처(±15°)여야 한다. ±180이면 혼이 반 바퀴 돌아간 것이다.

최종 영점은 16개 모두 이전 손과 ±11° 이내다. 측정 흔들림은 0.18° 이하였다.

**16관절 시험** (P 600 / D 200 / 350 mA, +10°): 모두 명령한 모터만 움직였다(다른 모터 ≤ 0.3°). 방향도 모두 맞았다(눈으로 확인). 모든 관절이 7.4~9.2°만 가고 1~2.5° 덜 간다. P 제어에 마찰이 겹친 것이고 누적되지는 않는다.
ID 14(엄지 가운데 마디)는 토크가 꺼지면 자기 무게로 약 79°까지 접힌다.

참고 이미지: [`../images/leap_motor_ids.png`](../images/leap_motor_ids.png) (`user_pc/scripts/render_leap_ids.py`, 메시는 dex-urdf `f5e7132`).

## 4. 검지 끊김

증상: 검지가 중간에 멈춤. 힘은 빠지지 않음.
도구: `leap_manus --log-csv logs/run1.csv` → `python3 -m leap_teleop.tools.analyze_log logs/run1.csv --joints 0 1 2 3 --current-limit 350`.
CSV에는 글러브 원값, 명령, 실제 전송값(관절 범위 제한·속도 제한 뒤), 현재 위치, 전류가 틱마다 들어간다.

| | run1 (SDK 캘리브레이션 전) | run2 (후) |
|---|---|---|
| 검지 MCP > 40°일 때 글러브 **PIP < 5°** | **60%** | **1%** |
| 전류가 상한에 붙음 (stall) | 없음 | ID 3에서 0.7% (주먹 끝) |
| 명령 − 전송값, 상위 5% (속도 제한 120°/s) | 17~47° | 14~52° |
| 전송값 − 현재 위치, 상위 5% | 7~10° | 7~9° |

- **부딪힘이 아니었다.** 전류는 상한에 붙지 않았다.
- **원인은 글러브 PIP였다.** 중간까지만 굽히거나 pinch를 하면 `IndexPIPStretch`가 0에 붙었다(예: MCP 87°, PIP 0°, DIP 52°). 그러면 LEAP 검지 가운데 마디가 펴진 채로 남는다. 11/03과 같은 증상이다.
- 우리 ROS 노드는 **integrated 모드**다. Manus 문서에 따르면 이 모드는 앱이 글러브 캘리브레이션을 직접 처리해야 한다. 그런데 `ManusDataPublisher.cpp`에는 캘리브레이션을 불러오는 코드가 없다. Dashboard 캘리브레이션은 Core 쪽에 저장된다.
- 조치: ROS 노드를 끄고 `third_party/manus/Python/examples/sdk_client.py` → `1`(Integrated) → `C` → `H`(Right) → `S` → 단계마다 `E`/`P` → `F`. 그 뒤 ROS 노드를 다시 켜도 유지됐다. `.mcal`은 저장하지 않았다(`K`를 누르지 않음). 글러브 전원을 껐다 켜도 유지되는지는 모른다.
- 남은 것: 빠르게 움직일 때 속도 제한(120°/s) 때문에 LEAP이 최대 0.5초 늦다. SDK 캘리브레이션 뒤 글러브 DIP 범위가 6~61° → −17~31°로 줄었다(주먹에서는 비율로 80°까지 감).

| 글러브 (편 손 → 주먹) | 이전 | 지금 |
|---|---|---|
| ThumbCMCStretch | 50.3 → 4.1 | 46.9 → 51.9 (5°만 변함) |
| ThumbIPStretch | −10.1 → 26.3 | −11.0 → 14.2 |

- 그때 노드 로그: `Quantum Battery phase DEAD`, 수신 93~99 Hz(정상 120), `74% of data is discarded`가 한 번. 배터리 부족 상태에서 캘리브레이션한 영향일 수 있다.

## 6. 손목 뒤집기: 홈에서 손가락이 위로

목표: home 자세에서 LEAP 손가락이 아래를 향했는데, 위를 향하게 한다.
코드: `OMY_Tactile_Robot_PC/omy_leap_bringup`의 `omy_ai_wrist_flip.launch.py`. 실행 명령은 `user_pc/README.md` 2단계 4번에 있다.

**확인한 구조**
- D405는 `link6` 몸통에 붙어 있다 (`omy_f3m_arm.urdf.xacro:210`). 플랜지와는 별개다. 그래서 카메라는 joint6이 돈 만큼만 돈다. 순정 부품으로 카메라 위치를 옮길 방법은 없다.
- leader의 `joint_trajectory_command_broadcaster`는 `/leader/joint_trajectory`에 `leader 위치 + offsets`를 실어 보낸다 (`joint_trajectory_command_broadcaster.cpp:329`). joint6 offset만 바꾸면 follower = leader + offset이 된다. relay 노드도, Homing Offset 변경도 필요 없다. 녹화되는 state와 action이 둘 다 follower 기준이고 URDF/TF와도 맞는다.

**1차: joint6 +π** (손 장착은 그대로, 카메라는 아래)
- 손목은 잘 뒤집혔다. 하지만 leader를 한쪽(+ 방향, "왼쪽")으로 돌리면 follower가 더 안 돌았다.
- 처음 의심한 `Collision detected` 로그는 원인이 아니었다. 충돌 노드만 격리해서 ready 자세로 joint6을 −180~180° 돌려 봐도 판정은 한 점에서만 났다.
- **원인: follower joint6 모터(YM070)의 Min/Max Position Limit = ±262144 pulse = ±π.** `get_dxl_data`로 읽었다. 공장 초기값이다 (eManual). URDF에는 ±2π로 적혀 있지만 Goal Position은 모터 한계에서 잘린다. home π가 한계 끝이라 + 쪽 여유가 0이었다.
- 모터 한계를 넓히는 방법(EEPROM)은 손목 케이블 안전 근거가 없어서 보류했다.

**2차 (채택): LEAP 기구 오른쪽 90° + joint6 +π/2**
- 손가락은 위를 향한다. 카메라는 90°만 돌아 손 옆에 온다.
- leader 기준으로 +90° ~ −180°까지 돈다. 양쪽 다 움직였다 ✅
- 바뀐 값은 leader offset의 joint6과 home/ready의 joint6, 두 군데뿐이다(π/2). 나머지는 순정 `9f84095` 복사본이고, Robot PC에 설치된 순정과 diff로 확인했다.
- 녹화하면 joint6이 π/2 근처다. 장착 상태가 다른 데이터와 한 데이터셋에 섞지 않는다.

**주의**
- 이번에 launch를 띄운 셸에는 `RMW_IMPLEMENTATION`이 없어서 DDS로 떴다. User PC(LEAP, Cyclo)와 같이 쓰려면 `export RMW_IMPLEMENTATION=rmw_zenoh_cpp` 후 띄운다.
- leader의 self-collision 검사는 leader 원래 각도(offset 전)와 그리퍼 모델로 판단한다. 실제 follower와 joint6이 90° 다르다. 오늘은 막힌 적이 없지만 정확하지 않다.
- Robot PC 변경: `/workspace/omy_ws/src/omy_leap_bringup`에 새 파일을 넣고 빌드만 했다. ROBOTIS 순정 파일과 모터 설정은 바꾸지 않았다.

## 7. 손목 카메라 (D405)

- 연결: OMY `Camera` 포트 → User PC USB. `8086:0b5b`, S/N `335122272125`, FW 5.12.14.100. `/dev/video2`~`7` (`video0`·`1`은 노트북 내장 웹캠).
- **USB 2.0(480M)으로만 잡혔다.** Belkin 허브·QinHeng 허브 어느 쪽에 꽂아도 USB2 쪽에 붙었다. 노트북 본체 USB3 직결이나 USB3 케이블은 아직 시험하지 않았다. OMY를 다시 켜면 카메라가 USB에서 사라져서 다시 꽂아야 했다.

- 실행: `ros2 launch realsense2_camera rs_launch.py camera_namespace:=camera camera_name:=cam_wrist [enable_depth:=false depth_module.color_profile:=424x240x30]`

- `backend-hid.cpp ... Failed to read busnum/devnum` 경고는 노트북 내장 HID 센서 때문이라 무시해도 된다.
- 측정 (작은 rclpy 구독자로 6초. 큰 이미지는 `ros2 topic hz`가 값을 못 낸다):

## 8. 미해결: Humble ↔ Jazzy `rmw_zenoh` 데이터 불통 (Cyclo를 막음)

- 증상: User PC(Humble)에서 zenoh(`client`, `tcp/10.42.0.241:7447`)로 붙으면 `ros2 topic list`와 `ros2 topic info`(Publisher count: 1)에는 `/joint_states`, `/leader/joint_trajectory`가 보인다. 그런데 **메시지는 0개**다(`echo --once` 무응답, 6초 0 Hz). 같은 셸에서 User PC 안의 Humble 토픽(`/leap/*` 43.5 Hz, 카메라 30 Hz)은 잘 받는다.
- 원인(추정, 강함): `ros-humble-rmw-zenoh-cpp` 0.1.11은 타입 해시 자리에 `TypeHashNotSupported`를 넣는다(라이브러리 문자열로 확인). Jazzy는 실제 해시(`RIHS01_...`)를 넣는다. 탐색은 되지만 데이터 key expression이 달라 이어지지 않는다. 11/03에 남긴 "Humble rmw_zenoh ↔ Jazzy 호환 확인"이 이것이다.
- 영향: Cyclo 컨테이너(`robotis/cyclo-intelligence:1.4.5`)는 Jazzy다. 그래서 Cyclo에서는 반대로 **팔은 보이고 손(`/leap/*`)·카메라는 안 보일 것**으로 예상한다(`[미검증]`, 이미지 받는 중에 멈춤). 텔레옵 자체는 영향 없다(팔 루프는 Robot PC 안, 손 루프는 `leap_teleop` 안).
- 후보:
  1. **DDS로 통일** (설치 없음, 먼저 시도): Robot PC `omy_ai` 셸 `RMW_IMPLEMENTATION=rmw_fastrtps_cpp ROS_DOMAIN_ID=30`, User PC 기본 RMW + `ROS_DOMAIN_ID=30`, Cyclo 컨테이너 `/root/.bashrc`도 Fast DDS. 표준 메시지는 Humble↔Jazzy DDS가 대개 통한다. 위험: USB 랜 위 DDS 탐색, Robot 컨테이너에 `rmw_fastrtps_cpp`가 있는지.
  2. User PC에서 Manus 노드 + `leap_teleop` + realsense를 **Jazzy 컨테이너**로 (반나절 정도. Manus ROS2 패키지를 Jazzy로 빌드해야 함).
  3. User PC를 Ubuntu 24.04 + Jazzy로 (10/09 PC 구성).

## 9. Cyclo 설치 상태 (User PC)

- `~/cyclo_intelligence` 받음 (install.sh). 이미지 `robotis/cyclo-intelligence:1.4.5` pull 도중 멈춤. GPU 없음 → `docker-compose.override.yml`이 `runtime: runc`로 바꿔 준다.
- 손목만 쓰는 로봇 config를 `~/cyclo_intelligence/shared/shared/robot_configs/omy_f3m_leap_config.yaml`에 넣었다 (레포 원본에서 `cam_front`·`cam_side` 제거, 손목 토픽 `color/image_raw/compressed`). 레포 원본은 그대로다.
- **1.4.5는 녹화·UI가 s6 서비스로 자동 실행되고, zenoh 설정을 컨테이너 `/root/.bashrc`에서 읽는다.** 기본값은 로컬(`transport/shared_memory/enabled=true`)이라 Robot PC 라우터에 안 붙는다. 실행표 B8의 `source /workspace/omy_env.sh; cyclo_intelligence` 대신 `.bashrc`의 원격 예시 줄을 `tcp/10.42.0.241:7447`로 풀고 `docker restart cyclo_intelligence` 해야 한다 (컨테이너를 다시 만들면 초기화). 8절이 풀리기 전에는 의미가 없다.
- `LEAP_NO_ZENOH=1`이 `~/.bashrc` 기본값이다. zenoh로 기록하려면 Manus 노드 셸과 `leap_manus` 셸 **둘 다** `unset LEAP_NO_ZENOH` 해야 한다(Manus 토픽도 같은 RMW여야 보인다).
