# 11/17 결과: Control Hub + 녹화기 첫 실물 시험

User PC: `jiwoo-950QDB` (Ubuntu 22.04, ROS 2 Humble). 목표는 `control_hub_and_recorder_overview.html`의 "실물 시험 가이드"를 처음 실물로 돌려 보는 것이었다.
팔(`omy_ai_wrist_flip`), LEAP, Manus, Paxini, 손목 카메라(D405)를 모두 hub에서 켜고, 녹화기로 에피소드 6개를 찍었다.
같은 날 녹화기 수정 2건과 hub UI 정리를 하고 `feat/control-hub-and-recorder`를 main에 합쳤다(`d7bcd0c`).

## 1. 준비와 연결

- `python3-venv` 가 없어 `uv venv` 로 환경을 만들었다. user_pc 시험은 `PYTHONPATH=src` 가 필요했다.
- Paxini `/dev/ttyACM0` 이 `0660 dialout` 이고 `jiwoo` 가 dialout 에 없어서 열리지 않았다. udev 규칙으로 `0666` 이 되게 했다.
- 녹화기 설정은 현장 사본 `recorder/config/rig.yaml` (git 무시)로 두고, 고친 값은 `rig.example.yaml` 에도 옮겼다.
- 연결 구성 (lsusb, 20:30 기준):

| 위치 | 장치 | 속도 |
|---|---|---|
| 3-2 (Belkin 5-in-1 쪽 허브) | Paxini 어댑터, Manus 동글 | 480M |
| 3-3 GenesysLogic 05e3:0610 | LEAP (FTDI), D405 | 480M |
| 3-3.2 QinHeng 1a86:8095 허브 | 그 안의 USB 10/100 LAN 1a86:e397 (`enx5414a7e483b1`, 로봇 랜) | 480M |

## 2. 녹화기 팔 스트림: 0개 → 400/300 Hz

**증상**: `check arm_state` 가 연결은 되는데 메시지가 0개. zenoh 키 `30/**` 전체를 구독해도 0개였다.

**원인**: `zenoh-ros2-sdk` 의 기본 세션이 zenoh **peer** 다. peer 는 라우터에서 서로를 알아낸 뒤 직접 연결하는데, Robot PC 노드들은 Docker 컨테이너 안이라 User PC 에서 그 주소로 갈 수 없다.

**고침** (`5575afe`):
- `arm_zenoh.py` 가 세션을 열기 전에 `ZENOH_CONFIG_OVERRIDE='mode="client"'` 를 넣는다. 사용자가 이미 mode 를 정했으면 건드리지 않는다. client 는 모든 것을 지정한 라우터(`10.42.0.241:7447`)를 거쳐 받는다. 3초에 1205개 확인.
- 첫 실행에서 두 팔 스트림이 동시에 SDK 를 열면, SDK 가 메시지 정의를 git clone 하는 중에 경합해 한쪽이 `JointTrajectory not found in registry` 로 실패했다. 하나씩 열도록 잠금을 넣었다.

**실측** (20:35 에피소드, 54.5 s):

| 토픽 | Hz | 최대 공백 | header.stamp |
|---|---|---|---|
| `/joint_states` (follower) | 399.7 | 8.6 ms | 있음 |
| `/leader/joint_trajectory` | 300.0 | 10.9 ms | **없음** (0) → `recv` 시각으로 정렬 |

`rig.yaml` 의 `arm_state.hz: 400`, `arm_action.hz: 300` 으로 고쳤다 (리뷰 14번).

18:52 에피소드(71 s)에서 본 팔 추종: follower 가 leader 를 약 **68 ms** 늦게 따라가고, 관절별 오차 평균 0.1~0.8°, 최대 11.6°.

## 3. 촉각: 보드 하나에 모듈 8개

- 설정은 보드 두 개(`tactile_a`, `tactile_b`)를 가정했는데, 실제로는 어댑터 보드 **하나**(펌웨어 `ADAPTER_FW02.26`)가 Thumb·Index·Middle·Little × Tip(52 taxel)·Middle(25 taxel) 8개 모듈을 다 보고한다. `board modules do not match config 'places'` 로 멈췄다.
- `tactile_a` 하나에 8개를 다 매핑했다. LEAP 은 손가락이 4개라 `Little-*` 를 `ring_*` 자리로 둔다. **4단계에서 손가락을 하나씩 눌러 확인해야 한다** (아직 안 함).
- 포트는 꽂는 순서에 따라 ACM 번호가 바뀌어 `/dev/serial/by-id/usb-PaxiniAdapte3_Paxini__Adapter_56226A779988-if00` 로 고정했다.
- 녹화 동안 손가락에 닿은 것이 없어 힘은 0 이었다(확인함).

## 4. 손목 뒤집기 "90° 안 돈다"

증상: 목요일(11/12)처럼 home 단계에서 손목이 90° 돌지 않는다.

확인한 것 (로봇은 켜지 않고 읽기만):
- Robot PC 의 `omy_leap_bringup` 은 로컬 commit `0244a1a` 와 바이트 단위로 같다. 11/12 이후 바뀌지 않았다. (`a0bf9bc` 는 같은 내용의 다른 commit)
- 로그상 leader 는 `leader_wrist_flip_controller_manager.yaml` 을 읽었고, home·ready 모두 joint6 = π/2 로 끝났다. 측정: follower joint6 91.4° = leader 1.4° + 90.0°.
- follower 모터 6개를 토크 OFF 상태로 직접 읽었다. Homing Offset 은 모두 **0** (바뀌지 않음). 꺼진 상태의 ID 6 위치는 **+91.7°**.

결론: 팔은 꺼질 때 마지막 손목 각도를 그대로 둔다. 11/12에는 0°에서 시작해 home 에서 90° 도는 게 보였고, 오늘은 이미 90°에서 시작해 돌 것이 없었다. 카메라가 손 옆, 손가락이 위를 향하는 것이 설계대로다 (LEAP 기구 90° + joint6 +90°).

hub 실행표에 **손목 90° / 순정** 선택을 넣었다. 순정(`omy_ai`)으로 녹화하면 `rig.yaml` 의 `rig.mount` 를 바꿔야 한다.

## 5. 연결이 끊긴 뒤 남는 원격 프로세스

**17:xx 에 본 것**: USB 랜이 끊기자 hub 창의 ssh 가 죽어 "오류"가 됐지만, 컨테이너 안의 팔 launch 와 zenohd 는 계속 돌았다. hub 에서 "끄기"가 먹지 않았다(창이 이미 죽어서). Robot PC 에서 launch pid 에 SIGINT, zenohd 바이너리에 SIGINT/TERM 을 손으로 보내 정리했다.

**고침** (`b29e7b2`, 리뷰 4번):
- 원격 명령마다 `export CONTROL_HUB_ID=<id>` 를 먼저 붙인다. 자식 프로세스가 모두 물려받으므로 `/proc/*/environ` 으로 그 실행의 프로세스 트리를 찾을 수 있다.
  명령줄로는 찾을 수 없다: bash 가 `a && b` 의 마지막 명령으로 자신을 바꾸므로 스크립트 문자열이 프로세스 목록에서 사라진다 (컨테이너에서 `sleep` 으로 확인).
- hub 가 5초마다 Robot PC 에 묻는다 (0.28 s). 창은 없는데 Robot PC 에 남아 있으면 그 줄이 빨강 "연결 끊김 · Robot PC 에서 아직 도는 중"이 되고, **[끄기]**(Ctrl+C) → 안 꺼지면 **[강제 종료]**(SIGKILL). 정리하기 전에는 같은 것을 다시 켤 수 없다. "전체 끄기"도 이것을 끈다.
- 실제 Robot PC 컨테이너에 같은 꼬리표를 단 `sleep` 을 남겨 감지 → 끄기 → 막힘 해제까지 확인했다. 팔로는 아직 안 봤다.

**20:29~20:37 저녁 시험**: 랜이 4~5초씩 여러 번 끊겼지만 ssh 가 살아남았고(ServerAlive 5 s × 3), 팔·zenohd 는 hub 끄기로 정상 종료(exit 0)됐다. 위 기능이 실제 끊김에서 동작하는지는 다음에 본다.

## 6. USB 랜 불안정 (가장 큰 문제)

- QinHeng 허브(3-3.2) 와 그 안의 랜 어댑터가 `error -71` 로 **20:28~21:00 사이 19번** 끊겼다. 끊기면 로봇 ping·ssh·zenoh 가 4~5초 사라진다.
- 18:52 에피소드의 팔 공백 **6.4 s, 3.1 s** 가 이것이다. Robot PC 쪽 시각으로도 5.6 s, 2.3 s 가 비어 있어, 그 사이 데이터는 잃었다. 팔 자체는 계속 움직였다(확인함).
- **20:37:24**: 3-3.2 리셋이 실패하자(`cannot reset (err = -71)`, `attempt power cycle`) 커널이 위쪽 허브 3-3 을 통째로 껐다 켰다. 같은 허브에 있던 **LEAP(FTDI) 와 D405 도 빠졌다.**
  - 텔레옵: `Port is in use` → 종료하면서 Torque OFF 확인을 16개 모터 모두 못 받음 → `cut the 5V supply` 오류로 끝(exit 1). USB 가 없어진 상태라 확인이 불가능했던 것이다. 손 상태는 직접 보고 5V 를 껐다 켠다.
  - 녹화기: hand·glove·cam_wrist·arm 모두 "끊김". 20:46:48 에 한 번 더 같은 일이 있었다.
- **조치**: QinHeng 허브를 빼고, 로봇 랜 어댑터를 노트북 포트에 **직접** 꽂는다(가능하면 다른 칩의 USB 랜). LEAP·카메라와 같은 허브에 두지 않는다.
