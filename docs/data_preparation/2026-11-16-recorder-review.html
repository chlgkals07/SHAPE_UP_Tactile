읽는 법. 코드에서 확인한 것은 파일 경로를 적었습니다. 수치 중 계산값은 Python으로 냈고, 실측하지 않은 것은 미측정으로, 기억이나 검색 요약에 기대는 것은 UNVERIFIED로 표시했습니다.

녹화기 시험은 오늘 임시 환경에서 돌려 89개 통과를 확인했습니다. 장치 어댑터 세 개(팔, Paxini 다중 센서, RealSense)는 아직 실물에서 돌려 보지 않았습니다.

"최대한 다 받고 나중에 맞춘다"는 게 맞나?맞습니다. 단, 녹화할 때 이미 정해지는 것이 몇 가지 있습니다.
  • 손·글러브는 텔레옵 틱(50 Hz)으로만 남습니다. 글러브 120 Hz는 마지막 값을 반복 발행하는 것이라 실제 정보 손실은 작습니다.
  • 카메라는 JPEG 손실 압축(품질 95)이고, 해상도·fps와 깊이 끔이 녹화 때 고정됩니다.
  • 팔 action은 trajectory의 첫 점만 저장합니다.
  • 수신 시각을 찍는 순간의 지연(OS, 스레드 스케줄, GIL)은 나중에 되돌릴 수 없습니다. 이 부분은 11절에서 다룹니다.
Cyclo보다 우리 것이 낫다고 주장할 근거는?근거는 다섯 가지입니다.
  1. 촉각이 데이터셋에 들어갑니다. Cyclo는 기록만 하고 변환하지 않습니다.
  2. Humble↔Jazzy 문제가 팔 한 스트림으로 줄어듭니다.
  3. 손·촉각·카메라·글러브가 한 시계를 씁니다.
  4. 텔레옵 루프와 완전히 분리됩니다.
  5. 원시 바이트를 보존해서 다시 찍지 않고 재해석할 수 있습니다.
단, 영상 압축 효율, 크래시 내구성, 편집·업로드 도구, 추론 연계는 Cyclo가 낫습니다 (7절).
ROS를 안 쓰면?장점: 버전 문제 회피, 직렬화와 DDS 단계 제거, 장치 직접 제어, 장치 없이 시험 가능.
단점: rosbag·RViz·Foxglove를 못 쓰고, 카메라를 녹화기가 독점하며, 표준이 아닌 코드를 우리가 유지보수해야 합니다 (9절).
Paxini ROS 발행기를 만드는 것보다 낫나?녹화가 목적이면 낫습니다. 발행기는 세 문제 중 하나(촉각을 ROS로 내보내기)만 풀고, 버전 문제와 촉각 변환은 그대로 남습니다. 나중에 정책을 ROS로 돌리게 되면, 허브 뒤에 ROS 출력을 붙이면 됩니다 (10절).
User PC를 Jazzy로 올리면?지금은 권하지 않습니다.
  • Jazzy는 Ubuntu 24.04용이라 OS 업그레이드가 필요합니다.
  • 녹화기는 ROS 없이 팔을 받도록 설계했기 때문에 얻는 것이 적습니다.
  • 순서: 현장에서 zenoh SDK 확인 → 실패하면 Robot PC에 중계 노드나 User PC에 Jazzy 컨테이너 → OS 업그레이드는 5080 PC를 새로 꾸릴 때.
(13절)

판정: 이 장비 구성에서는 우리 녹화기가 맞습니다. 다음 현장에서 사용법 문서 5절의 5.1(특히 팔 두 스트림), 5.3(지연 실측), 5.4(10분 부하)를 통과하면 확정입니다.

1. 전체 구조

설계의 세 가지 원칙

  1. 원본 먼저. 녹화 중에는 받은 그대로 저장하고, 시간 맞추기·리샘플·특징 계산은 변환기에서 합니다. 같은 원본에서 fps, 촉각 표현, 시각 기준, 지연 보정을 바꿔 다시 뽑을 수 있습니다.
  2. 한 시계. 녹화하는 PC의 CLOCK_MONOTONIC 하나가 기준입니다 (clock.py). 같은 PC의 다른 프로세스(leap_teleop)가 찍은 시각도 그대로 비교할 수 있습니다. 벽시계는 에피소드마다 대응 한 쌍만 남깁니다.
  3. 텔레옵은 건드리지 않는다. 손의 안전 동작(hold / release)은 leap_teleop 안에 그대로 있습니다. 녹화기는 그 프로세스가 보내는 UDP를 받기만 하고, 받는 쪽이 없어도 텔레옵은 영향을 받지 않습니다 (user_pc/src/leap_teleop/record_sink.py).

5. 시간축 맞추기

5.1 모든 샘플에 남는 시각

샘플마다 두 시각을 남깁니다. 무엇을 기준으로 맞출지는 변환할 때 스트림별로 고릅니다.

  • t_recv_ns: 허브가 그 샘플을 손에 쥔 순간입니다. 항상 같은 monotonic 시계입니다.
  • t_src_ns: 장치나 보낸 쪽이 준 시각입니다. 출처는 mono / host_wall / remote_wall / none 중 하나로 표시합니다.

5.2 스트림별 시각 선택 (dataset.time)

모드규칙쓰는 곳
recv받은 시각 그대로기본. 팔, 카메라, 글러브
src장치 시각을 녹화 PC 시계로 옮김:
  • mono는 그대로 씀
  • host_wall은 에피소드의 (mono, wall) 대응으로 이동
  • remote_wall은 가장 지연이 작았던 샘플이 자기 수신 시각에 오도록 이동
remote_wall은 그 최소 전송 지연만큼 일정한 편향이 남고, 이는 latency_ms로 지웁니다.		손 (기본). 팔 state에 쓸 수 있음
respread일정한 속도로 내보내는 장치의 USB 뭉침을 폄. 뒤에서부터 t[i] = min(recv[i], t[i+1] − 주기). 주기는 뭉침 단위 추정값의 40번째 백분위수(살짝 짧게)촉각 (기본)

마지막으로 latency_ms(스트림별 지연 보정)를 빼고, 시각이 거꾸로 가지 않게 단조 증가로 고칩니다 (align.stream_times).

5.3 격자와 품질 기준

  • 시작: 녹화 시작 시각과 모든 스트림의 첫 값 중 가장 늦은 것. 손은 위치 피드백이 처음 있는 샘플을 씁니다. 끝: 정지 시각. 간격은 1/fps이고, 반올림 누적이 없게 곱한 다음 나눕니다.
  • 스트림마다 stale_max_ms와 stale_p99_ms, 카메라는 재사용 프레임 수와 쓰기에서 버린 수를 보고합니다.
  • 기본으로 제외하는 에피소드: 150 ms 넘게 오래된 값이 있음, 녹화 중 끊김, 강제 시작, 실패 표시.

5.4 지연 실측 (tactile-rec tap)

사건이 뚜렷한 에피소드를 따로 찍습니다. 손을 빠르게 쥐거나, 손끝으로 책상을 톡 칩니다. 도구는 스트림마다 활동이 솟는 순간(중앙값과 99번째 백분위수의 중간을 넘는 순간)을 찾고, 기준 스트림과 짝지어 시간 차이를 냅니다.

같은 순간이어야 하는 쌍만 보정합니다. 예를 들면 촉각 힘과 모터 전류, 손 위치와 카메라 움직임입니다. 명령 → 위치(모터가 따라가는 시간)처럼 물리적으로 원래 늦는 것은 보정하지 않습니다. UMI가 카메라 지연을 QR 코드로, 그리퍼 지연을 명령과 측정의 상호상관으로 재는 것과 같은 생각입니다.

9. ROS를 안 쓰는 것의 장단점

장점

버전 문제 회피. Humble↔Jazzy rmw_zenoh 타입 해시 불일치(Humble은 TypeHashNotSupported, Jazzy는 RIHS01_…)를 팔 한 곳에서만 상대합니다.

지연 단계가 적음. 촉각과 카메라는 ROS 발행 → 직렬화 → 미들웨어 → 역직렬화 단계 없이, 읽은 스레드가 바로 시각을 찍습니다.

장치를 직접 제어. Paxini 영점(자동 전송을 잠시 끄고 보정), 모듈 배치 검사, RealSense 노출 고정을 어댑터가 직접 합니다.

환경이 가벼움. 같은 코드가 User PC(3.10)와 학습 서버(openpi)에서 돕니다. ROS 설치가 필요 없습니다.

장치 없이 시험. 가짜 장치와 가짜 시계로 89개 시험이 몇 초 안에 끝납니다.

단점

ROS 도구를 못 씀. rosbag 재생, RViz, Foxglove, ros2 topic echo는 inspect·replay(Rerun)로 대신합니다.

장치를 독점. 녹화기가 카메라를 직접 열기 때문에 realsense2_camera 노드를 꺼야 합니다. 같은 카메라를 다른 ROS 노드(예: 포즈 추정)가 동시에 쓸 수 없습니다.

드라이버 기능을 직접 구현. 깊이 정렬, 필터 같은 카메라 노드 기능이 필요해지면 우리가 만들어야 합니다.

팔은 결국 ROS 메시지. zenoh SDK가 ROS를 흉내 내는 구조이고, SDK는 0.1.x로 젊습니다. 메시지 정의를 실행할 때 git에서 받아 오므로 첫 실행에 인터넷이 필요합니다.

확장 한계. 허브가 한 PC의 한 프로세스입니다. 장치가 다른 PC로 흩어지면 같은 시계 원칙이 깨집니다.

유지보수 부담. 표준이 아닌 코드를 우리가 관리합니다.

정리: 녹화 경로에서는 ROS를 빼는 것이 이득입니다. ROS 생태계와 이어야 할 때(정책을 ROS 노드로 돌리기, 다른 노드와 카메라 공유)를 대비해서, 허브의 latest() 뒤에 ROS 출력을 붙이는 길은 열어 두는 게 좋습니다. 녹화 경로는 그대로 두고 출력만 덧붙이는 방식입니다.

11. 잠재 문제

11.1 Python 과부하 (GIL)

녹화 중 한 프로세스 안에서 도는 것:

  • 장치 스레드: 시리얼 2, 카메라 2, zenoh 콜백(팔 2, 각 ~100 Hz, Python CDR 역직렬화), UDP 1
  • JPEG 인코딩 스레드: 카메라당 1
  • 웹: 이벤트 루프, 미리보기 JPEG 재인코딩(15 Hz), 상태 계산 10 Hz. health()는 2초 버퍼를 매번 훑습니다.
영향왜크기
수신 시각 흔들림장치 스레드가 읽기에서 돌아온 뒤 GIL을 얻어야 now_ns()를 부릅니다. CPython 기본 switch interval은 5 ms입니다수 ms 단위로 예상 미측정. 30 fps 스텝(33 ms)보다는 작지만, 90 Hz 촉각 주기(11 ms)와는 같은 크기입니다
프레임 버림JPEG 인코딩이 밀리면 큐(120장) 초과분을 버림cv2 인코딩은 GIL을 놓으므로 CPU 부족이 원인일 때만. dropped_write로 보임
텔레옵 루프 흔들림GIL은 공유하지 않지만 같은 CPU를 나눔. GPU가 없는 PC에서 JPEG 2채널 + 미리보기미측정. 텔레옵 50 Hz가 녹화 중에도 유지되는지 따로 봐야 함
메모리 증가숫자 샘플이 Python 객체로 쌓임10분에 수십~100 MB 추정

바로 쓸 수 있는 탐침: 손 스트림은 보낸 시각(t_src, 텔레옵)과 받은 시각(t_recv, 허브)이 같은 시계입니다. 따라서 t_recv − t_src의 분포가 곧 "UDP + 허브 스레드 대기"입니다. 부하를 걸었을 때(카메라 2대 + 미리보기 창 여러 개) 이 분포의 p99를 보면 GIL 영향을 숫자로 알 수 있습니다. check hand가 이미 delay_ms를 냅니다.

12. 더 강건하게 받는 방법

아래는 제안입니다. 지금 코드는 바꾸지 않았습니다. 위에서부터 비용 대비 효과가 큰 순서입니다.

#제안푸는 문제비용
1지연 실측을 정렬 시각과 같은 기준으로. tap이 dataset.time의 모드(respread/src)로 시각을 계산한 뒤 재도록 변경11.2의 과보정작음 (align.stream_times 재사용)
2부하 시험을 숫자로. 5.4 10분 녹화 중에 손 t_recv − t_src p50/p99, 텔레옵 루프 Hz, 카메라 dropped_write, CPU를 기록GIL·CPU 영향 가시화작음 (현장 절차)
3에피소드마다 동기 사건 넣기. 시작 직후 손끝으로 한 번 톡 치기를 수집 규칙으로. 매 에피소드에서 tap 차이를 자동 계산해 보고서에 남김지연이 에피소드마다 변하는지 감시작음
4숫자 스트림 주기적 저장. 몇 초마다 청크로 써서, 크래시가 나도 그 앞까지 남게크래시 손실중간 (writer만)
5무거운 장치를 별도 프로세스로. 카메라 캡처와 JPEG를 자식 프로세스로 빼고, 허브에는 인덱스만. 같은 PC면 monotonic 시계를 공유하므로 시각 설계가 그대로 유지됨 (손 UDP가 이미 그 예)GIL, 촉각 시각 흔들림중간. 2번 결과가 나쁠 때만
6카메라 지연은 화면 시계로 실측. UMI처럼 모니터에 ms 시계나 QR을 띄우고 찍어서, 프레임에 보이는 시각과 수신 시각의 차이를 잼카메라 지연 (가장 클 후보)작음
7노출 고정. exposure_us를 실제 값으로. 노출이 바뀌면 지연과 블러가 바뀜카메라 지연 흔들림설정만
8두 PC 시계 맞추기(chrony) 후 팔 state를 src로. action은 Robot PC 쪽 중계에서 시각을 붙이는 방법도 있음팔 네트워크 지연·흔들림중간
9텔레옵 프로세스 우선순위. leap_teleop에 nice나 CPU 고정. 녹화기가 손 제어를 흔들지 않게텔레옵 루프 흔들림작음
10시작 전 점검 추가. 손 clock_mismatch, 팔 실제 Hz, 카메라 ts_domain을 점검 항목에잘못된 설정으로 찍는 것 방지작음
11표시(mark) 기반 trim·구간. 변환기가 mark로 앞뒤를 자르거나 서브태스크를 나눔 (Cyclo의 구간 기능 대응)편집 도구 부족중간
12D405를 USB3로. 케이블·포트 확인카메라 fps하드웨어

13. User PC를 Jazzy로 올릴까?

답: 지금은 올리지 않는 것을 권합니다. 녹화기는 ROS 없이 팔을 받도록 만들었기 때문에, 올려서 얻는 것이 녹화에는 거의 없습니다. 반면 지금 동작하는 텔레옵 환경 전체를 다시 세우는 위험이 있습니다.

전제부터 확인합니다. Jazzy는 Ubuntu 24.04(Noble)용 배포판입니다. User PC는 22.04이므로 "Jazzy로 업데이트"는 사실상 OS를 24.04로 올리는 일입니다. 22.04에서는 Jazzy를 컨테이너로만 쓰는 것이 현실적입니다.

얻는 것잃거나 다시 해야 하는 것
24.04 + Jazzy
  • Robot PC와 rmw_zenoh로 바로 통신. ros2 topic echo로 팔이 보임
  • Cyclo를 다시 쓸 수 있음
  • Python 3.12라 최신 LeRobot 가능
  • zenoh SDK가 실패해도 대안이 생김
  • Manus ROS 2 패키지를 Jazzy로 다시 빌드. Manus SDK의 24.04 지원 UNVERIFIED
  • librealsense / realsense2_camera를 24.04에 설치 (커널 모듈 문제 가능성) UNVERIFIED
  • leap_teleop, Paxini, 녹화기 venv 재구성

권하는 순서

  1. 다음 현장에서 tactile-rec check arm_state / arm_action. 설치가 필요 없습니다. 되면 버전 문제는 녹화에서 사라집니다.
  2. 안 되면, Robot PC 컨테이너에 작은 중계 노드. 팔 토픽과 Robot PC 시각을 UDP나 순수 zenoh로 보냅니다. 바뀌는 것은 arm_zenoh.py 한 파일이고, 시각을 원천에서 붙일 수 있어 오히려 낫습니다.
  3. 또는 DDS로 통일(11/12 문서 후보 1번). 설치는 없지만 USB 랜 위 DDS 탐색이 미검증입니다.
  4. ROS 생태계 전체가 필요해지면(정책을 ROS 노드로, Cyclo 추론): User PC에 Jazzy 컨테이너를 두는 것이 우리 환경 규칙(벤더·ROS 스택은 Docker)에도 맞습니다.
  5. OS 업그레이드는 5080 PC를 새로 꾸릴 때 24.04 + Jazzy로 시작하는 것이 깔끔합니다. 단, 녹화기와 leap_teleop은 같은 PC에 있어야 같은 시계 원칙이 유지됩니다. 옮긴다면 손·글러브·촉각·카메라를 함께 옮겨야 합니다.
