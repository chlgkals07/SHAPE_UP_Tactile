Control Hub + 녹화기

OMY 팔, LEAP Hand, Paxini 촉각, 손목 카메라를 한 시간축으로 기록해 LeRobot 데이터셋을 만드는 두 프로그램과, 그 둘이 텔레옵에 붙는 방식을 정리한다.

녹화기 recorder/

모든 센서를 이 PC 의 시계 하나로 시각을 찍어 원본 그대로 저장한다. 정렬과 리샘플은 나중에 변환기가 한다.

명령 tactile-rec · 화면 :8800 · ROS 없음

Control Hub control_hub/

터미널 여러 개에 붙여 넣던 명령을 버튼으로 켜고 끈다. 프로세스는 tmux 가 붙들고, hub 는 리모컨이다.

명령 control-hub · 화면 :8700

텔레옵 user_pc/

글러브 → 리타게팅 → LEAP. 기존 프로그램이고, 녹화기에 손 값을 보내는 출력 하나(--record-udp)가 붙었다.

명령 leap-teleop · 50 Hz 루프

세 줄 요약

  1. 녹화기는 ROS 를 쓰지 않는 Python 프로세스 하나다. 팔은 zenoh 로, 손은 localhost UDP 로, 촉각은 serial 로, 카메라는 USB 로 직접 받는다. 받는 순간 CLOCK_MONOTONIC 으로 시각을 찍는다.
  2. 기록은 원본, 데이터셋은 변환. 에피소드 폴더에는 센서가 보낸 그대로(촉각 90 Hz 전부, 영상은 프레임별 JPEG)가 들어간다. 30 fps 격자에 맞추는 일은 tactile-rec convert 가 하고, 같은 원본에서 설정을 바꿔 다시 뽑을 수 있다.
  3. Control Hub 는 두 프로그램과 텔레옵, Robot PC 의 프로세스를 한 화면에서 순서대로 켜는 도구다. 녹화기도 hub 가 켜는 프로세스 하나이고, hub 의 "녹화" 메뉴 안에서 녹화기 화면이 그대로 열린다.

녹화기

센서마다 스레드 하나가 값을 받아 시각을 찍고, 한 객체(Hub)에 모은다. 기록, 화면, 나중의 정책 실행이 모두 같은 Hub 에서 읽는다.

핵심 생각 네 가지

시계는 하나

모든 샘플에 이 PC 의 CLOCK_MONOTONIC 을 찍는다. 벽시계는 에피소드마다 한 쌍(anchor)만 남긴다. NTP 가 시계를 고쳐도 기록이 뒤틀리지 않는다.

원본 그대로

촉각은 보드가 보낸 바이트를, 영상은 회전하지 않은 프레임을 저장한다. 해석 규칙이 틀렸어도 다시 찍지 않고 고칠 수 있다.

기록과 변환 분리

녹화 중에는 받는 일만 한다. 30 fps 격자, 지연 보정, 촉각 고주파 창은 오프라인에서 정한다.

조용히 실패하지 않기

끊김, 쓰기 실패, 버려진 패킷, 영점 실패가 화면과 episode.json 에 남는다.

Stream: 모든 장치의 공통 모양

어댑터가 할 일은 값을 손에 넣는 즉시 push() 를 부르는 것뿐이다. 시각 찍기, 2초 버퍼, 빠진 수 세기, 구독자에게 전달은 Stream 이 한다.

# recorder/src/tactile_rec/stream.py (요약)
def push(self, data, *, t_src_ns=NO_TIME, src_seq=NO_TIME, t_recv_ns=None):
    if t_recv_ns is None:
        t_recv_ns = self.clock.now_ns()            # 받은 시각: 이 PC 의 monotonic
    with self._lock:
        sample = Sample(t_recv_ns, self._count, data, t_src_ns, src_seq)
        if src_seq > self._last_src_seq + 1:       # 장치 번호가 건너뛰면 빠진 것으로 센다
            self._missed += src_seq - self._last_src_seq - 1
        self._buffer.append(sample)                # 최근 2초를 들고 있는다 (pre-roll)
        self._error = ""                           # 정상 값이 오면 오류 표시가 풀린다
        for fn in self._subscribers: fn(sample)    # 녹화 중이면 EpisodeWriter 가 여기 있다
샘플에 붙는 것뜻
t_recv_ns녹화기가 받은 시각 (monotonic ns). 항상 있다
t_src_ns장치가 준 시각. 없으면 -1. 어느 시계인지는 스트림 사양의 src_clock (mono, host_wall, remote_wall, none)
seq / src_seq녹화기가 센 번호 / 장치가 센 번호(카메라 프레임 번호, 텔레옵 틱)

리뷰 뒤 바뀐 것 (37d49f9). 전에는 잘못된 패킷·프레임이 counter 만 올리고 사라져서, 값이 전부 잘못돼도 스트림이 그냥 "없음"으로 보였다. 지금은 정상 값 없이 버려지는 값만 오면 reject() 가 이유를 오류 메시지로 올린다. counter(bad_packets, bad_frames, bad_messages, device_errors, subscriber_errors, clock_mismatch)는 센서 페이지에 실시간으로 나오고 에피소드마다 streams.<이름>.counters 에 저장된다.

장치 어댑터

arm_zenoh.py 팔 상태와 팔 명령 현장 미검증

zenoh-ros2-sdk 의 ROS2Subscriber 로 Robot PC 라우터에 직접 붙는다. 메시지는 SDK 스레드에서 콜백으로 온다.

  • JointState: 설정한 관절 이름 순서로 다시 줄 세운다. 설정한 관절이 메시지에 없으면 그 메시지를 버리고 오류로 올린다. NaN 을 관절각으로 기록하지 않기 위해서다.
  • JointTrajectory: 첫 point 를 쓴다. 값 7개 중 앞 6개가 팔, 마지막이 leader 트리거다.

시간 맞추기 (이론)

주기도 시계도 다른 다섯 센서를 30 fps 한 줄로 세우는 규칙. 직관, 식, 숫자 순서로 적는다.

1. 문제

데이터셋의 한 행은 "어느 한 순간에 로봇이 본 것과 한 것"이어야 한다. 그런데 센서는 제각각이다.

팔약 100 HzRobot PC 벽시계 (다른 PC)네트워크 지연, 두 PC 시계의 차이를 모름

촉각약 90 Hz없음USB 가 여러 샘플을 한꺼번에 넘긴다(bunching)
카메라30 fps호스트 벽시계 또는 hardware counter노출·전송·디코딩 지연(수십 ms)

2. 규칙: causal, 보간 없음

직관. 로봇이 실제로 움직일 때 정책은 "지금까지 도착한 값"만 본다. 학습 데이터도 그래야 한다. 미래 값을 쓰거나 앞뒤를 보간하면 실행 때 없는 정보가 섞인다.

식. 격자 시각을 gk = tstart + k / fps 라 하면, 스트림 s 의 k 번째 값은

i(k) = max { i : t_s[i] ≤ g_k }        # 그 시각 이전의 가장 최근 샘플
x_s[k] = sample_s[i(k)]
staleness_s[k] = g_k − t_s[i(k)]        # 그 값이 얼마나 오래됐나

코드에서는 np.searchsorted(times, grid, side="right") - 1 한 줄이다(convert/align.py pick_latest).

숫자 예. 격자가 33.3 ms 간격이고 손이 20 ms 간격이면 값의 나이는 0~20 ms 사이를 오간다. 촉각(11 ms 간격)은 0~11 ms. 어느 스트림이든 나이가 dataset.max_staleness_ms(기본 150 ms)를 넘는 스텝이 있으면 그 에피소드는 문제로 표시되고 기본으로 제외된다.

3. 스트림마다 어떤 시각으로 줄을 세우나

dataset.time 으로 스트림별로 고른다. 적지 않으면 recv 다.

세 번째가 팔에 해당한다. 두 PC 의 시계를 맞추지(chrony) 않아도 되는 대신, 최소 지연만큼은 모른다. USB 랜에서 수 ms 로 예상한다 현장 미검증.

respread: USB bunching 을 되돌리기

직관. 보드는 11 ms 마다 하나씩 만드는데 USB 는 33 ms 에 셋을 한꺼번에 준다. 받은 시각만 보면 셋이 같은 순간에 일어난 것 같다. 하지만 i 번째 샘플은 i+1 번째보다 적어도 한 주기 전에 만들어졌다.

식. 뒤에서부터

t[i] = min( recv[i],  t[i+1] − period )

주기는 burst 의 끝 시각 간격을 burst 크기로 나눈 값들의 40 백분위로 추정한다(프레임이 빠진 구간은 값이 길게 나오므로 중앙값보다 조금 아래를 쓴다).

왜 안전한가. 이 규칙은 샘플을 받은 시각보다 앞으로만 옮기고, 실제 만들어진 시각보다 앞으로는 가지 않는다. 프레임이 빠졌으면 실제 간격이 한 주기보다 길 뿐이라 경계가 느슨해질 뿐이다. 그래서 어떤 스텝도 자기 미래의 촉각 값을 보지 않는다.

4. 지연 보정

dataset.latency_ms: {cam_wrist: 35} 처럼 적으면 그 스트림의 모든 시각에서 35 ms 를 뺀다. 값은 추측하지 않고 tactile-rec tap 으로 잰다: 손끝으로 책상을 톡 치면 촉각 힘과 모터 전류가 같은 순간에 튀어야 하고, 손을 쥐면 손 위치와 카메라 움직임이 같은 순간이어야 한다.

보정하지 않는 것. 명령 → 위치(모터가 따라가는 시간), 글러브 → 명령(리타게팅)은 물리적으로 실제 있는 지연이다. 이것을 0으로 만들면 데이터가 거짓말을 한다.

5. 고주파 촉각 창

30 fps 한 스텝 안에 촉각은 3번 온다. dataset.tactile_hr: 3 이면 스텝마다 그 스텝 시각과 그 앞 1/3, 2/3 스텝 시각의 값을 함께 넣는다(observation.tactile.resultant_hr). 마지막 값이 스텝 시각의 값이라 여기에도 미래 값은 없다.

이 규칙이 어디서 왔고 무엇과 다른지는 참고 자료에, 4절의 지연값을 실제로 재는 방법은 지연 실측 실험에 있다.

지연 실측 실험 (논문용)

스트림마다 "일이 일어난 순간 → 녹화기가 받은 순간"과 "명령 → 실제 움직임"을 재서 표로 남긴다. UMI(Chi et al., RSS 2024) 부록 A 의 방법을 우리 장치에 옮긴 계획이다. 11/17 추가 계획. 아직 실행 안 함

왜 해야 하나

UMI 보다 우리가 더 필요하다. UMI 는 손에 든 GoPro 하나가 영상·IMU·그리퍼 폭을 같이 찍어서, 수집한 데이터 안의 스트림끼리는 지연이 0이다(논문 §IV "Hardware-specific latency"). 그래서 지연은 로봇에서 실행할 때만 맞춘다. 우리는 데이터 자체를 실물 로봇의 분산된 장치(다른 PC 의 팔, USB 촉각, USB 카메라)로 모은다. 지연이 녹화 데이터에 이미 들어 있고, 실행 때도 다시 생긴다.
  • 효과가 크다. UMI 는 같은 정책에서 지연 맞추기만 끄자(측정값을 0으로) 동작이 떨리고, 던지기 성공이 105/120 = 87.5% 에서 69/120 = 57.5% 로 떨어졌다(§V-B, Fig. 8).
  • 촉각 논문의 근거가 된다. "접촉 순간"을 영상·손 위치와 맞춘다고 주장하려면 그 정렬 오차가 몇 ms 인지 수치가 있어야 한다. 30 fps 한 스텝이 33.3 ms 이므로, 카메라 지연이 그 정도면 촉각과 영상이 한 스텝 어긋난다.
  • 지금은 비어 있다. dataset.latency_ms 는 {} 이고, 팔 remote_wall 변환은 "가장 짧았던 전송 지연"을 0으로 둔다(시간 맞추기 3절). 이 둘을 채우는 실험이다.

지금 있는 도구의 한계. tactile-rec tap 은 사건이 시작되는 순간(onset)을 스트림마다 찾아 서로의 차이만 낸다. 그래서 카메라 하나의 절대 지연(L1)이나 명령 → 위치의 실행 지연(E1, E2)은 나오지 않는다. 표의 없음 세 가지가 새로 만들어야 하는 것이다. 코드는 아직 쓰지 않았다.

실험 순서 (제안)

  1. L2 팔. 1분 동안 ping 해서 왕복의 중앙값과 p95 를 적는다. 가능하면 chrony 로 맞춘 뒤 check arm_state 의 delay_ms 와 비교한다.
  2. L3 손. check hand 30초.
  3. L1 카메라. 녹화 설정(해상도, fps, exposure_us)을 데이터 수집 때와 같게 두고, 모니터의 QR 을 60초 이상 찍는다. 프레임마다 lcamera 를 구해 중앙값, p95, spread 를 적는다. 노출을 바꾸면 지연도 바뀌므로 설정마다 따로 잰다.
  4. L4 촉각. 실물 시험 6단계의 톡 치기. 카메라에 손끝이 보이게 둔다.
  5. E1 · E2 실행. 텔레옵으로 손을 천천히 쥐었다 폈다, 팔을 좌우로 흔드는 30초짜리 에피소드를 각 3개 찍는다.
  6. 닫힘 검사. 잰 값을 latency_ms 에 넣고 다시 변환한 뒤 tap 을 돌린다. "같은 순간이어야 하는 쌍"의 차이가 0 근처로 줄어야 한다. 줄지 않으면 측정이나 보정 방향이 틀린 것이다.
  7. 재현성. 다른 날 한 번 더 잰다. 값이 바뀌면 USB 포트, 케이블, 부하를 같이 적는다.

변환기

tactile-rec convert: 원본 에피소드 폴더 → LeRobot v2.1 데이터셋(또는 확인용 npz). 학습 서버의 openpi 환경에서 돌린다.

한 에피소드가 지나는 길

  1. 읽기 convert/load.py Episode: episode.json 과 스트림별 npz, 영상 index.
  2. 스트림별 시각 정하기 align.stream_times: dataset.time 의 모드, latency_ms, 그리고 뒤로 가는 시각을 눌러 단조 증가로 만든다.

Control Hub

가이드의 명령을 YAML 한 파일에 옮겨 적고, 브라우저에서 순서대로 켜고 끈다. hub 가 죽어도 로봇은 계속 돈다.

왜 tmux 인가

  • hub 와 프로세스의 수명을 뗀다. hub 를 고치느라 재시작해도 팔과 손은 계속 돈다. 다시 띄우면 도는 창을 그대로 알아본다.
  • 언제든 터미널로 돌아간다. tmux -L shapeup attach -t hub 로 같은 창에 들어가 직접 볼 수 있다.
  • 끄는 방식이 가이드와 같다. "끄기"는 그 창에 Ctrl+C 를 보낸다. leap_* 는 그때 Torque OFF 를 한다.
  • Robot PC 에 아무것도 설치하지 않는다. 원격 프로세스도 User PC 의 창에서 ssh 로 돈다.

버튼 하나가 실행되기까지

  1. 브라우저가 POST /api/process/<id>/start 를 보낸다. 보내는 것은 id 와 고른 옵션(flag id), 체크한 확인 항목뿐이다. 명령 문자열은 받지 않는다.
  2. supervisor.py 가 막을 이유를 본다: requires(먼저 떠 있어야 하는 프로세스나 점검), conflicts(같이 켜면 안 되는 것), confirm_start(사람이 체크해야 하는 것).
  3. command.py 가 한 줄을 만든다: env 의 줄들 && cmd + 고른 flag 의 인자. 원격이면 ssh -tt, 컨테이너면 그 안에서 docker exec -it.
  4. tmux.py 가 그 줄을 스크립트 파일로 써서 새 창에서 실행하고, 출력을 로그 파일로 보낸다.

lines   = envs[proc.env]                       # 예: source /opt/ros/jazzy/setup.bash, export ...
script  = " && ".join([*lines, proc.cmd + flags])

  • 전: devices.*.recorder_stream 은 화면 문구에만 쓰였다. 녹화 중 촉각 보드가 빠져도 hub 의 촉각 칸은 그대로였고, 녹화기는 스트림 오류를 로그에 찍지도 않았다.
  • 후: 녹화기가 상태가 바뀔 때마다 [tactile-rec] stream tactile_a: error (read failed: …) 한 줄을 찍는다. hub 는 그 줄을 읽어 그 스트림을 가진 장치 칸을 빨강(error, stale)이나 노랑(slow, off)으로 만든다. 일반 사건은 60초 뒤 사라지지만 이 표시는 녹화기가 ok 라고 할 때까지 남고, 녹화기가 꺼지면 사라진다.
  • conflicts: 확인 도구(check_*)는 녹화기와 같은 장치를 연다. 특히 check_hand 는 같은 UDP 포트를 열어 패킷을 나눠 가졌다. 녹화기와 모든 확인 도구가 서로 conflict 다.
  • hint 하나 삭제: "Connection to … closed" 는 원격 프로세스를 정상적으로 끌 때마다 걸렸다.
  • 끌 때 확인 (eaacb33): 녹화기에 confirm_stop 을 넣었다.
알려진 한계. 원격 프로세스는 ssh -tt … docker exec -it … 로 돈다. 이더넷이 끊기거나 "강제 종료"로 창을 닫았을 때 컨테이너 안의 프로세스가 같이 끝나는지는 코드로 보장하지 못한다 현장 미검증. 팔 bringup 을 강제 종료한 뒤에는 "로봇 중복 실행 확인" 도구로 남은 노드가 없는지 본다.

한 화면에서 쓰기

hub 의 "녹화" 메뉴 안에서 녹화기 화면이 그대로 열린다. 프로그램은 여전히 둘이고, 화면만 하나다.

이번에 넣은 것. hub 왼쪽 메뉴에 녹화가 생겼다. 녹화기가 떠 있으면(checks.recorder_ui 가 정상) 그 화면을 frame 으로 보여 주고, 꺼져 있으면 켜는 버튼으로 안내한다. 이 페이지에서는 오른쪽 점검 띠를 숨겨 폭을 다 쓴다.

왜 코드를 합치지 않았나

방법비용잃는 것
hub 안에 녹화기 화면을 frame 으로 (선택)hub 화면 파일 3개에 수십 줄. 녹화기 코드는 그대로없음. 녹화기는 hub 없이도 그대로 쓴다
hub 가 녹화기의 API 를 불러 자기 화면을 그림녹화 페이지(미리보기, 촉각 맵, 키 처리)를 hub 쪽에 다시 만든다같은 화면이 두 벌이 된다
한 프로세스로 합침크다hub 를 재시작하면 녹화가 끊긴다. tmux 로 수명을 뗀 이유가 사라진다. ROS 없는 venv 와 hub 의 환경도 섞인다

동작 방식

  • frame 의 주소는 checks 에서 link 가 있는 http 점검의 주소다(예시 설정의 recorder_ui, http://127.0.0.1:8800/).
  • hub 를 태블릿에서 열면 127.0.0.1 은 태블릿 자신이 된다. 그래서 주소가 localhost 면 hub 를 연 호스트 이름으로 바꿔서 연다. 이 경우 녹화기도 --host 0.0.0.0 으로 띄워야 한다.
  • frame 은 녹화기가 뜰 때 한 번만 불러온다. hub 의 1초 갱신이 녹화 화면을 다시 그리지 않는다.
  • 녹화기의 키(Space 등)는 frame 안을 한 번 누른 뒤에 듣는다. 브라우저의 focus 규칙이다.
  • 녹화기는 다른 사이트가 보낸 변경 요청을 Origin 으로 막는다. frame 안의 요청은 녹화기 자신의 origin 에서 나가므로 통과한다.
확인 범위. 가짜 녹화기를 띄우고 hub 화면을 열어, 꺼져 있을 때의 안내와 켜졌을 때 녹화기 화면이 hub 안에 뜨는 것을 스크린샷으로 확인했다. 다만 이 Mac 에는 tmux 가 없어 hub 는 프로세스를 켤 수 없는 상태였다. hub 버튼으로 녹화기를 켜고 끄면서 화면이 바뀌는 것, frame 안에서의 키 입력과 실제 녹화는 Ubuntu 에서 봐야 한다 (실물 시험 가이드 0단계).

참고 자료

시간 맞추기와 지연 실측의 근거. 각 항목에 우리 코드의 어느 부분과 이어지는지, 그리고 원문을 어디까지 읽었는지 적는다. 11/17 추가

읽은 범위. UMI 는 원문 PDF 에서 §IV(PD1), §V-B, 부록 A 를 읽었다. 나머지는 검색 결과의 요약만 보았다. 인용하기 전에 원문을 확인한다.

1. 고르는 규칙: causal, 보간 없음

자료내용우리와의 관계읽은 범위
Zero-order hold (Wikipedia), NPTEL Sampling and Reconstruction. 교과서: Oppenheim & Schafer, sampling 장다음 샘플이 올 때까지 값을 계단처럼 들고 있는 복원. first-order hold(선형 보간)와 비교align.pick_latest 가 이 계단을 격자 시각에서 읽는다요약
LeRobot record.py 녹화 루프 (공식 huggingface/lerobot)1/fps 루프마다 get_observation() 으로 최신 값을 읽고 busy_wait 로 주기를 맞춘다같은 규칙을 녹화 중에 바로 한다. 우리는 원본을 남겨 나중에 한다요약 (미러 코드)
docs/data_preparation/2026-11-13-cyclo-analysis.mdCyclo 의 causal 리샘플, staleness 보고, frame_reuse우리가 그대로 가져온 원본레포 문서

2. 대조군: 가장 가까운 시각끼리 묶기

자료내용우리와의 관계읽은 범위
ROS message_filters ApproximateTime (ROS wiki), ROS 2 문서토픽별 queue 머리에서 가장 늦은 메시지를 pivot 으로 잡고 시각 차이가 가장 작은 조합을 찾는다. 파라미터가 없다가까우면 미래 메시지도 묶는다. 분석에는 좋지만 정책 학습에서는 실행 때와 달라진다요약

3. 다른 시계 옮기기

자료내용우리와의 관계읽은 범위
E. Olson, "A Passive Solution to the Sensor Synchronization Problem", 2010. 구현 예: hanley6/time_sync센서가 협조하지 않아도, 받는 쪽에서 "offset 은 모르고 지연은 항상 양수"라는 조건만으로 시계 차이를 추정한다팔의 remote_wall 변환(offset = min(t_recv − t_src))과 촉각 respread("받은 시각보다 앞으로만")가 같은 생각이다. 가장 가까운 이론요약

4. 지연 실측

자료내용우리와의 관계읽은 범위
C. Chi et al., "Universal Manipulation Interface", RSS 2024. 프로젝트 페이지부록 A: 카메라는 QR 시각, 고유감각은 로봇 시각 또는 ½ ping, 실행 지연은 명령과 측정의 cross-correlation. 실행 때는 가장 늦은 스트림 기준으로 맞추고(PD1.1) 실행 지연만큼 앞선 action 을 버린다(PD1.2). 지연 맞추기를 끄면 던지기 87.5% → 57.5%지연 실측 실험의 L1, L2, E1, E2 가 이 방법을 옮긴 것이다원문 §IV PD1, §V-B, 부록 A
P. Furgale, J. Rehder, R. Siegwart, "Unified Temporal and Spatial Calibration for Multi-Sensor Systems", IROS 2013. Kalibr wiki카메라와 IMU 의 time offset 을 continuous-time batch 추정으로 공간 보정과 함께 구한다. 초기값은 두 센서가 본 각속도의 상관tap 의 "같은 사건이 두 스트림에 언제 보이나"를 정식으로 푼 것이다. 더 정밀하게 갈 때 본다요약
T. Qin, S. Shen, "Online Temporal Calibration for Monocular Visual-Inertial Systems", arXiv 2018 (학회 미확인)보정판 없이 time offset 을 상태에 넣어 온라인으로 추정센서 사이 offset 을 패턴 없이 잡는 다른 길요약
