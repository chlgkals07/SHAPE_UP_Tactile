정책 실행기: π0.5 추론에서 하드웨어 실행까지

GPU 서버의 π0.5 정책과 OMY 팔 + LEAP 손 rig 사이에서 일하는 프로그램이다. 서버 쪽 짝(openpi-RLT 의 pi05_omy_leap config)은 5절에서 설명한다. 센서 값을 학습 데이터와 같은 모양으로 묶어 WebSocket 으로 보내고, 돌아온 50 행짜리 action chunk 를 30 Hz 격자에 맞춰 실행한다. 이 문서는 전체 흐름, 각 단계를 그렇게 만든 이유, 실제로 추가한 파일과 코드를 설명한다.

설계 원칙 세 가지

1. 학습과 같은 입력. 정책은 녹화기가 만든 데이터셋으로 학습한다. 그래서 실행 중 관측도 녹화기 변환기(convert_episode)와 같은 규칙으로 만든다. 같은 시각 규칙, 같은 손 feedback 필터, 같은 JPEG 압축을 쓰고, 이를 테스트로 bit 단위까지 확인했다.

2. 시간은 격자 위에서. 행동은 30 Hz 격자의 정해진 tick 에만 나간다. 늦은 행은 버리고 기록하며, 밀린 행을 몰아 보내지 않는다.

3. 모든 판단을 기록하고 따로 검사한다. 관측·요청·응답·채택·전송·지연·상태 변화가 trace(jsonl)에 한 줄씩 남는다. 실행기와 별개로 작성한 감사기가 그 trace 를 규칙에 맞는지 검사한다.

왜 정책 실행기가 LEAP USB 를 직접 열지 않나

leap_teleop 에는 이미 관절 한계 clip, 속도 제한, 모터 캘리브레이션, 종료 때 Torque OFF, 입력이 끊겼을 때 hold → safe pose 로 가는 StaleGuard 가 있다. 실행기가 USB 를 직접 잡으면 이 기능들을 다시 만들어야 한다. 실행기 프로세스가 죽었을 때 손을 지킬 독립된 감시자도 없어진다. 그래서 손에는 "입력 소스" 하나(UDP)만 추가했다. 텔레옵과 정책은 같은 출력 경로를 쓰고 입력만 다르다.

3한 사이클의 흐름

사용자가 UI 에서 시작(arm)을 누른 뒤 한 chunk 가 실행되기까지의 순서다. 스레드 세 개가 일을 나눈다.

  • tick 스레드(Runner._tick_forever)는 30 Hz 격자에서 Executor.tick 을 부른다.
  • 추론 스레드(InferenceWorker._serve)는 관측을 만들고 서버에 묻는다.
  • Hub 스레드들은 장치에서 받은 샘플을 버퍼에 쌓는다.
  1. 요청. Executor 가 tick 시각 now 로 chunks.request(now) 를 부른다. 상태는 HOLD 가 된다.
  2. 관측 정렬. 추론 스레드가 깨어나 ObsAligner.align(t_obs) 로 그 시각의 state(22)와 카메라 이미지를 만든다. 오래됐거나 빠진 stream 이 있으면 요청하지 않고 다음 tick 에 다시 시도한다.
  3. 전송과 대기. PolicyClient.infer 가 관측을 msgpack 으로 보내고 응답을 기다린다. 기다리는 시간은 최대 infer_timeout_ms(1000 ms)다.
  4. 응답 검사. check_reply 가 actions 의 모양 (50, 22), float 형, 모든 값이 유한한지 본다. 통과하면 ActionChunk 가 된다. 이 chunk 에는 관측 시각 t_obs_ns 와 도착 시각이 붙는다.
  5. 채택. 다음 tick 에 Executor 가 chunk 를 꺼낸다. chunk 가 너무 오래되지 않았는지(500 ms)만 본다. 통과하면 그 tick 이 행 0 의 시각이 되고, 상태는 RUNNING 이 된다. 관절 범위와 속도 제한은 실행기가 아니라 장치 제어기(LEAP 드라이버의 clip·slew)가 맡는다.
  6. 실행. 이어지는 tick 마다 행 1, 2, … 를 보낸다. 앞 K = 10 행만 쓴다. 예정보다 10 ms 넘게 늦은 행은 보내지 않고 late 로 기록한다.
  7. 다음 요청. K 행을 다 쓴 tick 에 다음 요청을 하고 HOLD 로 간다. 1번으로 돌아간다.

왜 겹치지 않는 chunk 실행부터 하나

추론을 겹쳐 돌리거나(다음 chunk 를 미리 요청) RTC 처럼 chunk 를 이어 붙이면 HOLD 가 줄어든다. 대신 "어느 행이 어느 관측에서 나왔는가"를 따지기가 훨씬 어려워진다. 먼저 가장 단순한 방식으로 시간 의미와 장치 연결이 맞는지 trace 로 증명한다. 지연이 얼마나 되는지(HOLD 비율)도 실측한다. 더 복잡한 방식은 그 뒤에 결정한다.

클라이언트를 직접 만든 이유

문제openpi-client 를 쓰면우리 구현
numpy 버전openpi-client 는 numpy<2.0 을 요구한다. 녹화기 환경은 numpy 2.2.6 이라 한 환경에 둘 수 없다wire 코덱(msgpack_numpy, 47줄)만 출처와 Apache-2.0 표기를 붙여 wire.py 로 옮겼다. 형식이 같아 수정하지 않은 서버와 그대로 통한다
timeoutinfer() 가 recv() 를 무기한 기다린다. 서버가 멈추면 실행기도 멈춘다recv(timeout=) 로 기다림을 제한한다. 넘으면 InferTimeout
늦은 응답timeout 뒤 같은 연결로 다음 요청을 보내면, 앞 요청의 늦은 응답을 새 요청의 답으로 읽을 수 있다timeout 이 나면 연결을 닫는다. 늦은 응답은 닫힌 연결로 와서 버려진다. 의도적 버그 M03 으로 확인
오류 구분—텍스트 프레임 → ServerError (FAULT), 끊김 → Disconnected, 시간 초과 → InferTimeout (재시도)
# inference.py · PolicyClient.infer (요약 없이 실제 코드)
def infer(self, obs, timeout_s):
    if self.connection is None:
        self.connect()
    try:
        self.connection.send(wire.packb(obs))
        raw = self.connection.recv(timeout=timeout_s)
    except TimeoutError as error:
        self.close()
        raise InferTimeout(f"no reply within {timeout_s * 1000:.0f} ms") from error
    except ConnectionClosed as error:
        self.close()
        raise Disconnected(f"server closed the connection: {error}") from error
    if isinstance(raw, str):
        self.close()
        raise ServerError(raw)
    return wire.unpackb(raw)

연결은 websockets 17.4 의 동기 클라이언트 connect(..., max_size=None, compression=None, legacy=True) 로 연다. 연결을 오래 유지하는 직접 연결은 17.1 부터 legacy=True 가 필요하다(설치된 소스에서 확인). 그래서 의존성은 websockets>=17.1, Python ≥ 3.11 이다.

시작할 때의 검사

  1. 연결 + metadata. 연결되면 서버가 먼저 보내는 metadata 를 받는다. 받지 못하면 StartError.
  2. manifest 대조. checkpoint 를 학습한 조건(manifest: fps, joint_names, cameras, mount, hand_action, pred_horizon, checkpoint, norm_stats_id)이 실행기 설정과 같은지 비교한다. 한 항목이라도 다르면 시작하지 않는다. 다른 rig 설정으로 학습한 정책을 잘못 돌리는 일을 막는다.
  3. warm-up. 0 state 와 0 이미지로 요청을 한 번 보내고 결과는 버린다. 실제 π0.5 는 첫 요청에서 JIT 컴파일로 수 초가 걸린다. 이 시간이 첫 chunk 의 timeout 으로 나타나지 않게 한다.

팔 action 은 leader 팔 값이고 state 는 follower 팔 값이라 둘 사이에 오프셋이 있다. 손 action 은 모터에 쓴 값(sent)이라, 물체를 쥐면 측정값과 차이가 생긴다. 그래서 측정 state 에 대한 상대값으로 학습하는 편이 자연스럽다고 봤다. 어느 쪽이 나은지는 학습해서 비교해야 하므로 플래그(use_delta_joint_actions, delta_action_dims=6 이면 팔만)로 남겼다. 실행기 계약은 어느 쪽이든 같다. Group.push 는 출력 변환을 앞에 넣으므로, AbsoluteActions 는 32차원 출력에서 먼저 돌고 그다음 22차원으로 잘린다.

def tick(self, now_ns, grid_ns=None):
    grid_ns = now_ns if grid_ns is None else grid_ns
    with self._lock:
        if self.state not in (RUNNING, HOLD):
            return
        if self.chunks.fault:
            self._fail(now_ns, self.chunks.fault)
            return
        if self.active is None and not self._adopt(now_ns, grid_ns):
            self._hold(now_ns, "waiting for a chunk")
            return
        self._step(now_ns, grid_ns)

정상 동작(잡기, 빠른 쥐기)을 막아 오히려 멈춤을 만들 수 있다. openpi 예제 클라이언트도 이런 거부를 하지 않는다. 그래서 chunk 거부는 빼고, 관절 범위·속도 제한은 장치 제어기에 맡긴다. 손은 leap_teleop 드라이버가 모든 명령에 관절 범위 clip 과 관절 속도 slew 제한을 건다(leap_v1.py command_degrees). 정책 모드도 같은 경로다.

시각 규칙

  • 행 i 의 예정 시각 = 채택 tick 의 격자 시각 + i·dt. 응답이 도착한 시각을 기준으로 잡지 않는다 (M06).
  • 몰아 보내지 않는다. tick 이 늦어 행 3, 4 를 놓쳤으면 둘 다 late 로 기록하고 지금 시각에 맞는 행만 보낸다. 밀린 목표를 한꺼번에 보내면 손이 급하게 움직인다 (M05).
  • 예정보다 tick_jitter_ms(10 ms) 넘게 늦으면 그 행도 보내지 않는다.
  • K 행을 넘지 않는다. H = 50 행이 와도 앞 10 행만 쓰고 다음 관측으로 다시 묻는다 (M07).
평가 중에 찾은 버그: 행을 깬 시각 기준으로 셌다

처음에는 chunk 시작 시각을 tick 스레드가 실제로 깬 시각으로 잡았다. 그런데 그 tick 이 늦게 깨면 다음 tick 들이 이 시작 시각에 비해 이르게 된다. Hub 화면을 띄운 채 돌린 실측 trace 에서 행 2 와 3 이 23.318 ms 간격으로 나갔다(최소 허용 dt − jitter = 23.333 ms). 감사기가 이것을 잡았다.

수정(9b73f4a): tick 스레드가 예정 격자 시각을 같이 넘긴다(tick(now, grid)). 행 번호와 예정 시각은 격자로 계산하고, 늦음은 실제 시각으로 잰다. tick 스레드는 예정 시각보다 일찍 깨지 않으므로 두 전송 사이가 dt − jitter 보다 짧아질 수 없다. 수정한 뒤 60 s 실측 두 번에서 위반은 0 이었다.

# runner.py · 30 Hz 격자
def _tick_forever(self):
    dt_ns = self.cfg.dt_ns
    next_ns = self.clock.now_ns()
    while not self._stopping.is_set():
        now_ns = self.clock.now_ns()
        if now_ns < next_ns:
            self._stopping.wait((next_ns - now_ns) / 1e9)
            continue
        self.executor.tick(now_ns, next_ns)
        next_ns += dt_ns * ((now_ns - next_ns) // dt_ns + 1)

RTT 란

round-trip time. 실행기가 요청을 보내기 시작한 순간부터 응답을 다 받은 순간까지의 시간이다. 실행기 쪽 시계로 잰다(trace 의 reply.rtt_ms). 그 안에는 다음이 다 들어 있다.

  • 요청 직렬화(msgpack)와 업로드. 요청 하나는 약 305 KB 다. 대부분 이미지(424×240×3 바이트)다.
  • 서버 추론. infer_ms 로 따로 오고, 약 70 ms 다.
  • 응답 다운로드. (50, 22) float 라 약 4 KB 로 작다.

그래서 RTT − infer_ms 가 통신에 쓴 시간이다. probe 중앙값으로 보면 서버 안에서는 3.0 ms(71.5 − 68.5), Mac + 터널에서는 46.5 ms(117.2 − 70.7)다.

해석: 망을 거치면 중앙값으로 약 50 ms 가 더해진다

서버를 "거쳐서" 느려지는 것이 아니다. 서버 추론 시간은 두 경우 모두 약 70 ms 로 같다. 더해진 약 50 ms 는 Mac ↔ GPU 서버 사이 망과 ssh 터널의 비용이다. 빈 요청 왕복이 22.6 ms 이므로 나머지 약 25–30 ms 는 305 KB 이미지 업로드로 추정한다 (분해는 미검증). 중앙값보다 꼬리가 더 문제다. p99 가 318.7 ms 로 K 10 행(333 ms)에 가깝다. 그래서 같은 망이면 HOLD 가 늘고, 가끔 늦은 chunk 가 나올 수 있다.

요청 수가 601 → 395 로 준 것도 이 때문이다. 학습 안 한 가중치라 chunk 가 모두 거부되고, 사이클이 "응답 대기 tick + 1" 이 되어서 대기가 길어진 만큼 요청이 줄었다. 실제 User PC 의 망은 Mac 과 다를 수 있다 미검증.

지연이 실행에 주는 영향 (계산값)

Mac 기준으로 정리하면 이렇다.

  • 망 왕복(RTT − infer)이 약 50 ms 이고, 서버 추론이 약 70 ms 라서 RTT 중앙값은 약 120 ms 다.
  • 겹치지 않는 chunk 실행(K 10, 30 Hz)에서 응답 대기 tick 은 w = ⌈RTT/dt⌉ 이고, 사이클은 w + K tick 이다.
  • 마지막으로 실행되는 행은 사이클 길이만큼 지난 관측으로 만든 것이다.

  • 꼬리가 더 문제다. p99 사이클에서는 HOLD 가 50% 다. 로봇이 0.33 s 멈췄다 움직이는 stop-and-go 가 커진다.
판단: 기준선에서는 충분히 작다. tactile 반응은 이 루프로 하지 않는다

지금 기준선 π0.5 에는 tactile 이 입력으로 들어가지 않는다 (state 22 + 카메라). 그래서 tactile 지연은 지금 제어 루프에 없고, 기준선 실험에서 망 50 ms 는 critical 하지 않다.

tactile 이 핵심인 반응은 망을 줄여도 이 구조로는 안 된다. 미끄러짐에 쥐는 힘으로 반응하는 동작은 수십 ms 안에 일어나야 한다 (사람 반사 약 60–80 ms 로 알려져 있다, 미검증). 정책은 약 2 Hz 로 재계획하고 333 ms 를 열린 루프로 실행한다. 이런 반응은 VLA 가 아니라 User PC 나 손 쪽의 로컬 고속 루프(50–100 Hz 이상)에 두고, VLA 는 느린 상위 계획을 맡는 구조가 맞다.

tactile 을 VLA 입력에 넣는 경우에도, 촉각이 행동에 반영되기까지 "RTT + 최대 K × dt" (약 0.4–0.5 s)가 걸린다. 여기서도 망보다 K 와 열린 루프 실행이 지배적이다.

로컬 추론 (5080 예정) 과 원격 서버

  • 코드는 그대로 된다. 실행기는 policy.endpoint 로 websocket 을 열 뿐이고, ssh 는 원격 서버를 127.0.0.1:8000 처럼 보이게 하는 장치다. GPU 서버 smoke 가 이미 "같은 기계, ssh 없음" 구성이었다.
  • 5080 PC 에서 할 일: openpi-RLT feat/omy-leap 설치(uv), checkpoint 복사, XLA_PYTHON_CLIENT_MEM_FRACTION 설정. 원하면 Control Hub 에 openpi 서버 프로세스 항목을 추가한다.
  • 예상: 망 약 50 ms 와 그 꼬리는 없어지지만 추론은 느려진다.
    • 배치 1 추론은 메모리 대역폭에 묶인다. 5080 은 약 960 GB/s, RTX PRO 6000 은 약 1.8 TB/s 다(사양은 기억 기준).
    • 그래서 같은 openpi 구현이면 5080 추론을 약 100–140 ms 로 추정한다 미검증.
    • 공개 자료에 5080·RTX PRO 6000 의 π0.5 수치는 없었다. 5090 은 최적화 스택 기준 약 18 ms 가 보고됐다. 즉 GPU 보다 추론 스택 차이가 더 크다.
  • 비교 기준: 중앙값이 아니라 RTT p99 와 HOLD 비율. 로컬 추론이 약 150 ms 를 넘으면 원격 서버가 나을 수 있다 (추정).
